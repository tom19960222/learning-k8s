# §0 給沒參與的人的三分鐘版本

Ceph 內建三種 mClock scheduler profile，決定 OSD 忙不過來時要優先服務誰：`high_client_ops` 偏袒前台的使用者流量，`high_recovery_ops` 偏袒後台的資料修復，`balanced` 是預設值，兩邊各半。官方文件把該怎麼選講得很清楚，但從來沒有人給過數字——真的壞掉一台機器的時候，換 profile 到底能讓使用者少痛多少？

我們在 Azure 上開了一套八台 NVMe 機器的 Ceph cluster，花了大約 230 小時，對三個 profile 注入同一批故障：拔掉一顆 OSD、隔離整個機櫃、讓 OSD 反覆上下線。量四件事：資料修復完要多久、使用者感受到的延遲惡化幾倍、最長卡住不動幾秒、故障期間還跑得到多少吞吐。

**結論是：用這些指標，量不到差別。**

這句話有兩個但書，都不能漏。

第一，這是「量不到」，不是「證明相等」。八顆 OSD、本機 NVMe、每格只有兩到三個樣本，我們沒有做等價性檢定（§13）。

第二，**量不到的最近原因很可能不是 cluster 太小，而是這次的配置讓 mClock 幾乎沒有出手的餘地。** 有三件事擋在它前面：它管不到副本寫入、保底份額從來沒緊繃過、修復的併發度被另一個參數卡死（§5.4）。所以最準確的講法是「在這個配置下，三個 profile 沒有機會表現出差別」——而不是「三個 profile 沒有差別」。

我們把「故障型態 × 壓力等級」的每一種組合當成一組來比。十二組裡三個 profile 都拿到至少兩筆資料，其中觀測條件完全一致、可以乾淨比較的有八組。這八組全部呈現同一個型態：同一個設定重跑的波動，大於或等於三個 profile 之間的差距。

最乾淨的一組是「單顆 OSD 下線 + 4K 隨機讀寫 + 低壓力」：三個 profile 的修復時間中位數是 759、815.5、751 秒，彼此最多差 64.5 秒；而光是 balanced 自己跑三次，就從 671 秒橫跨到 889 秒，差了 218 秒。

這不是「還沒測出來」。八組全是這個型態，而且每一次「看起來有差」的時刻，補上第三筆資料之後都被吃掉。

唯一活下來的訊號只有一個：在完全不限速的壓力下拔掉一顆 OSD 時，`high_client_ops` 確實保住了較高的使用者吞吐，達成率 1.017，對上 balanced 的 0.905 和 high_recovery_ops 的 0.883，三組值域完全不重疊，方向完全符合 mClock 的設計意圖。但它只有兩到三個樣本、不是事前登記的主要指標，而且同一個指標換到「機櫃隔離」情境就不成立。這不足以作為上線切換的理由，只能當下一輪的假說。

所以該做什麼：維持預設的 `balanced`，不必為故障情境切換 profile。真正該動手的是另外兩件事：

- **確保壞掉的 OSD 乾脆下線，不要反覆上下線。** 乾脆掉一顆時使用者的 p99 延遲是 8.5 到 13 毫秒，約十二分鐘就修復完成；OSD 反覆上下線時是 304 到 1,585 毫秒，而且從來沒有自己結束過。絕對延遲差了三十倍以上，這是整份報告裡最大的單一效果量，比三個 profile 之間的任何差距都大得多。
- **別讓 OSD 容量參數停在編譯預設值。** Ceph 原始碼裡寫死的 21,500 IOPS 跟你買的是哪顆硬碟毫無關係，而這個數字是 mClock 所有配額的分母。不過要說清楚：Ceph 開機時自己量出來的替代值（本次八顆是 6,057～6,646）也不準，它只跑了半秒鐘，真實能力大概是它的兩倍（§2.2）。這條建議的方向站得住，但我們沒有跑過「不校準」的對照組，所以講不出它值多少。

報告的後半跟 mClock 無關，但大概更有用：這種故障注入實驗本身有幾個會讓你白做工的坑，我們全部踩過了——包括一道八天內誤報六次、真陽性掛零的自動檢查，以及一整組因為「量測工具被自己注入的故障打斷」而完全報廢的測試。

## 幾個名詞，先講定義

報告正文盡量不用內部代號，但有幾個 Ceph 與統計用語會反覆出現，先講清楚：

- **OSD** — Ceph 裡負責保管資料的常駐程式，一顆磁碟通常對應一個。八台機器各一顆，就是本次的八顆 OSD。
- **PG**（placement group） — Ceph 把資料分成一群一群來管理的單位。「所有 PG 回到 `active+clean`」等於「副本全部補齊、狀態正常」，本報告用它來判定修復完成。
- **backfill** — 一顆 OSD 掛掉後，把缺少的副本重新複製到其他 OSD 的過程，也就是本報告講的「修復」。
- **p99 延遲** — 把所有 I/O 請求的延遲排序後第 99 百分位的值，代表「最慢的那 1% 有多慢」。比平均值更能反映使用者實際的卡頓感受，所以本報告一律看 p99，不看平均。
- **變異係數** — 標準差除以平均值，用來衡量一批數字有多分散，越小代表越一致。本報告用它判斷「同樣的測試重跑幾次，結果穩不穩」。
- **campaign** — 這次橫跨十天、約 230 小時的整批實驗的總稱。

# 第一部：mClock profile 到底有沒有差

# §1 這次在測什麼

## 1.1 為什麼 OSD 需要一個排程器

一顆 OSD 同時要服務兩種完全不同的工作。一種是前台的使用者讀寫，慢了會被立刻感覺到。另一種是後台的資料修復。當一顆 OSD 掛掉，它上面的資料副本數不足，cluster 必須把缺的副本重新複製到別處（backfill），這件事不做完，再壞一顆就會掉資料。

這兩件事搶同一批磁碟和 CPU。修復做得越兇，使用者越痛；修復做得越溫和，暴露在「再壞一顆就完蛋」的時間窗越長。mClock 就是決定這個取捨的排程器。

它給每一類工作三個參數：**reservation**（保底，無論如何都給的最低份額）、**weight**（保底之外，剩餘資源怎麼分）、**limit**（上限，最多不能超過多少）。Ceph 把常用組合包成三個現成的 profile，這樣管理員不必自己調六個數字。

## 1.2 三個 profile 差在哪

以下是 Ceph v19.2.2 實際寫死的值。「client」是使用者流量，「recovery」是資料修復，「best effort」是 scrub 之類的雜項。

| profile | client | recovery | best effort |
|---|---|---|---|
| `balanced`（預設） | 保底 50%，權重 1，無上限 | 保底 50%，權重 1，無上限 | 保底 0%，權重 1，上限 90% |
| `high_client_ops` | 保底 **60%**，權重 **2**，無上限 | 保底 40%，權重 1，無上限 | 保底 0%，權重 1，上限 70% |
| `high_recovery_ops` | 保底 30%，權重 1，無上限 | 保底 **70%**，權重 **2**，無上限 | 保底 0%，權重 1，無上限 |

差距看起來不小：使用者流量的保底份額從 30% 到 60%，差了一倍。直覺上，故障期間切到 `high_client_ops` 應該能讓使用者明顯少痛，代價是修復拖比較久；切到 `high_recovery_ops` 則相反。

這份報告要回答的就是：這個直覺在真實故障下，能量到多大的效果。

三個 profile 都可以在執行中切換，不必重啟 OSD。但「設定送出去」不等於「八顆 OSD 都生效」，所以每次切換之後我們都會逐顆確認，確認不過就不開始測。

## 1.3 為什麼值得花 230 小時

因為文件只告訴你方向，沒告訴你幅度。「偏袒使用者流量」如果實際上只換到 3% 的延遲改善，那在故障當下手動切 profile 這個動作就沒有意義，因為它本身就有風險，而且要有人在半夜醒著做。反過來，如果能換到兩倍，那就值得寫進 runbook。

沒有幅度，就沒有辦法決定要不要做。這是整個實驗的動機。

# §2 測試環境與判準

## 2.1 機器與 cluster

| 項目 | 規格 |
|---|---|
| Ceph 版本 | **v19.2.2** (squid)　※注意不是本 repo submodule 釘的 v19.2.3 |
| 位置 | Azure `japanwest`，共 15 台 VM、88 vCPU |
| OSD 機器 | 8 台 `Standard_L8s_v3`，每台 8 vCPU / 64 GiB RAM / 1.92 TB 本機 NVMe |
| OSD 數量 | **8 顆**（每台機器一顆，磁碟獨占） |
| 控制面 | 3 個 mon + 2 個 mgr |
| 壓力來源 | 4 台 fio client |
| 作業系統 | Ubuntu 22.04，kernel 6.8 系列（`linux-generic-hwe-22.04`） |
| pool 設定 | 副本數 3，`min_size` 2，PG 固定 128，autoscaler 關閉 |
| 故障域 | 8 顆 OSD 編成 **4 個合成機櫃**，每櫃 2 顆 |

兩個刻意的選擇要先講明白，因為它們限制了結論能推廣到哪裡。

kernel 特意選 `linux-generic-hwe-22.04` 而不是 Azure 專用的 `linux-azure`。因為使用者端的 I/O 走的是 krbd（在 kernel 裡的 RBD client），kernel 換掉，被測的程式碼路徑就換掉了。這裡要對齊的是正式環境，不是雲廠商的最佳化。

「機櫃」是合成的。所有機器掛在同一張網卡、同一個子網路下，所謂的機櫃隔離是用防火牆規則做出來的。這代表機櫃隔離的結果不能拿去推論真正跨可用區的網路故障。真實的跨區故障會有頻寬、延遲、封包遺失的差別，這裡完全沒有。

## 2.2 一個必須先講的數字：OSD 能力校準

mClock 的所有份額都是相對值。「保底 50%」的 50% 是誰的 50%？是這顆 OSD 的 IOPS 天花板。這個天花板由參數 `osd_mclock_max_capacity_iops_ssd` 決定。

Ceph 編譯進去的預設值是 **21,500 IOPS**。這是原始碼裡寫死的常數，跟你插的是哪顆磁碟沒有任何關係。所以 Ceph 會在 OSD 每次開機時自己跑一小段測試，量出真實值來覆蓋它。本次八顆量到 **6,057 到 6,646 IOPS**（平均 6,439），彼此的變異係數只有 3.19%，相當一致。

campaign 開始前，我們把這八個值逐顆鎖住並關掉開機自動重測，讓十天下來所有測試都跑在同一組數字上。

**但這個開機測試量到的東西，比它的名字所暗示的窄很多。** 讀原始碼可以看到它寫死的內容：寫 3,000 個 4 KiB 的區塊，單一執行緒，直接寫進 OSD 的儲存層——不經過網路、不經過副本複製、也不經過 mClock 自己。以量到的速率反推，整段計時只有大約 **0.47 秒**。Ceph 在測試結果超出合理範圍時印的警告訊息裡，也明白建議改用 fio 之類的工具另外量。

用本報告自己的資料就看得出它偏低。健康狀態下量到的cluster 天花板是 63,634 IOPS（4K、讀寫 7:3、副本 3、八顆 OSD），把它拆回每顆 OSD 頭上：

| 每顆 OSD 每秒處理的動作 | 數量 |
|---|---|
| 使用者寫入（自己當主副本） | 2,386 |
| 副本寫入（別顆 OSD 轉過來的） | 4,773 |
| **寫入小計** | **7,159** |
| 使用者讀取 | 5,568 |
| 合計 | 12,727 |

開機測試量的是純寫入。而實際上每顆 OSD 一邊服務著 5,568 個讀取，一邊還做掉 7,159 個寫入——**已經超過鎖定的 6,439**。所以真實能力至少是量到值的 1.1 倍，把讀取一起算大約是 2 倍。

三個數字並排，比較誠實的講法是這樣：

| 每顆 OSD 的 IOPS | 這是什麼 | 可信度 |
|---|---|---|
| 21,500 | 編譯預設值 | 跟硬體無關的常數 |
| 6,057 ～ 6,646 | 開機自動測試 | 0.47 秒、單執行緒、只走儲存層 |
| 約 7,200 ～ 12,700 | 由cluster 天花板拆回每顆 OSD | 本報告推算，非直接量測 |

所以編譯預設值 21,500 對這套硬體確實太高，大約高了 1.7 到 3 倍。而我們鎖進去的那組值，則是偏低了大約一半。兩個都不對，只是錯的方向相反。

**我們是往低的方向錯的，而這個方向對實驗不利。** 保底份額是三個 profile 差最多的地方，容量設得越低，保底就越容易被滿足、越不會變成真正的限制。換句話說，這個為了嚴謹而做的校準動作，有可能反過來讓要測的效應變得更難看見。這件事留到 §5.4，因為要先看過結果才講得清楚。

## 2.3 負載

兩種 I/O 形態，各自有四個壓力等級。

| 形態 | 參數 | 低 | 中 | 高 | 極限 |
|---|---|---|---|---|---|
| **4K 隨機讀寫**（讀寫 7:3） | 每台 client 4 個 job、佇列深度 16，共 16 job | 15,908 IOPS | 31,817 | 50,907 | 不限速（實測天花板 63,634） |
| **1 MiB 循序寫** | 每台 client 2 個 job、佇列深度 8，共 8 job | 594 MiB/s | 1,187 | 1,899 | 不限速（天花板 2,374） |

四台 client 各自有一顆 300 GiB 的 RBD image，亂數種子固定為 4242，所以不同 profile 之間打的是同一組 I/O 位址序列。每段測試跑 300 秒，前面加 30 秒暖機。

「極限」這一檔是閉迴路，不設速率上限，能跑多快跑多快。它跟其他三檔有本質差異，後面 §7 會說明為什麼這一檔的比值指標會騙人。

## 2.4 注入哪些故障

| 故障 | 做了什麼 | 想模擬的真實情況 |
|---|---|---|
| **單顆 OSD 下線** | 停掉一顆 OSD，手動標記為 out，觀察 backfill 到完成 | 一顆磁碟壞掉 |
| **機櫃隔離** | 用防火牆規則把一個合成機櫃的 2 顆 OSD 從網路上切開 | 一個機架的交換器掛掉 |
| **整台 node 隔離** | 同上，但範圍是一整台機器 | 單機失聯 |
| **反覆上下線** | 讓 OSD 週期性地掉線又回來 | 網路不穩或硬體間歇性故障 |
| **循序流量競爭** | 大 I/O 循序寫的同時觸發修復 | 備份視窗撞上故障 |
| **混沌注入** | 固定種子隨機打多種事件 | 多重故障疊加 |

每次注入都受一個觀測上限保護：時間到了不管修復完成沒有都收工，避免一格卡死拖垮整個排程。單顆 OSD 下線、機櫃隔離、node 隔離的上限是 2700 秒，循序流量競爭是 3150 秒。這個上限後來變成一個大陷阱，見 §4.2。

## 2.5 量哪四件事

| 指標 | 定義 | 白話 |
|---|---|---|
| **修復完成時間**（秒） | 從注入動作開始，到所有 PG 回到 `active+clean` | cluster 花多久才把資料補齊 |
| **延遲惡化倍率** | 故障期間的 p99 延遲 ÷ 注入前 60 秒窗的 p99 延遲 | 使用者感覺慢了幾倍 |
| **最長停頓**（秒） | 所有 client 的每秒 IOPS 加總為零的最長連續區間 | 最久一次完全不動是多久 |
| **回填吞吐量**（MB/s） | 修復期間的資料複製速率 | 修復做得多快 |

> 一個命名上的教訓，先講在這裡。前兩份中期報告裡，「修復完成時間（秒）」和「回填吞吐量（MB/s）」在英文欄位名稱裡都叫 `recovery`。後來對帳時一度以為兩份文件的數字互相矛盾，追下去才發現是同名異物，兩邊各自算對，只是講的是不同的東西。這份報告一律用上表的中文全名，絕不共用「recovery」這個詞。

延遲惡化倍率的分母是「同一次執行裡、注入之前那 60 秒」，不是另外跑的基準測試。這是刻意的：用同一次執行的前段當分母，可以抵銷機器狀態隨時間漂移的影響。這個設計決定後來被證明是整個量測架構最正確的一件事，理由見 §8。

## 2.6 事前就講好的判定門檻

這些數字在開始跑之前就登記好了，過程中沒有調整過。

| 指標 | 要大於多少才算「有差別」|
|---|---|
| 最長停頓 | 差 2 秒以上 |
| 回填吞吐量 | 差 25% 以上 |
| 修復完成時間 | 差 300 秒或 20%，取大者 |
| 延遲惡化倍率 | 依正規化規則判定（不另設毫秒門檻） |

另外兩條是給營運用的絕對判準，跟 profile 比較無關：停頓 5 秒以上就算值得記錄的事件，30 秒以上代表 VM 裡的作業系統可能開始出現 I/O 問題。

事前登記這件事本身很重要。如果門檻是看到資料之後才訂的，那「有沒有差別」就變成作文比賽。

## 2.7 可信度的防線

除了上面的門檻，還有四道機制在防止結果被污染：

- 每次切換 profile 之後，逐顆確認八顆 OSD 都真的生效，沒生效就不開跑。
- 跑對照組：完全不注入故障、只跑穩態負載，三個 profile 各三次。如果連沒故障的時候都量得出差別，那就代表量測本身有問題。
- 交錯排程：三個 profile 不是一個跑完再換下一個，而是輪替，避免時間趨勢被誤讀成 profile 差異。
- 覆蓋率打卡：一個獨立的監看程式定期記錄「量測工具還活著」，事後可以證明資料沒有缺口。

對照組的結果先講，因為它決定了後面所有數字的可信度。

穩態 4K 跑滿 36 次，三個 profile 的 IOPS 平均值最大只差 0.03% 到 0.48%，p99 延遲最大只差 0.011 到 0.699 毫秒。穩態循序完成 35 次，吞吐量最大差 0.30% 到 1.58%，p99 延遲最大差 0.841 到 2.447 毫秒。不過同一格重跑之間的落差最大到 8.913 毫秒，比組間差距還大。

**沒有故障的時候，三個 profile 確實量不出差別。** 這正是應該的：mClock 的份額只有在資源不夠分的時候才會咬合。對照組成立，代表量測平台本身沒有系統性偏差，後面看到的（以及沒看到的）差異可以當真。

# §3 實驗計畫總表

一個「測試格」是一組固定的條件：故障型態 × I/O 形態 × 壓力等級 × profile。規劃了 63 個測試格、147 次基礎執行；過程中因為補樣本與救援重跑，追加到 177 次；實際完成 156 次。

| 無（對照組） | 4K 隨機 | 四檔 | 12 | 36 | ✔ 全數完成，三個 profile 無差別 |
| 無（對照組） | 循序 | 四檔 | 12 | 36 | ✔ 完成 35 次，一次待人工處理 |
| 單顆 OSD 下線 | 4K 隨機 | 低/中/極限 | 9 | 18 | ✔ 三檔皆可乾淨比較，**無法區分 profile** |
| 機櫃隔離 | 4K 隨機 | 低/中/極限 | 9 | 18 | ✔ 三檔皆可乾淨比較，**無法區分 profile** |
| 整台 node 隔離 | 4K 隨機 | 中 | 3 | 6 | ✔ 可乾淨比較，**無法區分 profile** |
| 循序流量競爭 | 循序 | 中/極限 | 6 | 12 | △ 中壓力可比（兩筆越過門檻但樣本不足）；不限速混用觀測上限，不可比 |

帳目要對得起來：177 次規劃 = 156 次完成 + 21 次未完成。那 21 次是混沌注入的 3 次（量測工具被自己注入的故障打斷，實際上取不到資料，見 §9），加上另外 18 次補樣本（分散在多個測試格，都是各自的第三或第四次，那些格子已有兩筆資料，補不補都不影響結論）。沒有任何一格是被悄悄丟掉的。

「無法區分 profile」是本報告最重要的四個字，§5 展開。

## 3.1 開跑之前凍結的預測

每一個區塊在開始跑之前都寫下了方向性預測並凍結，事後不得修改。這些預測不是隨口猜的，是從 mClock 的份額設計直接推出來的：如果 `high_client_ops` 給 client 的保底是 60%、`high_recovery_ops` 只給 30%，那故障期間前者的使用者延遲就該明顯比較低。

| 區塊 | 凍結的事前預測 | 推論依據 |
|---|---|---|
| 穩態對照（4K 與循序） | 三個 profile 應完全等效 | 沒有修復流量時，使用者流量是唯一活躍的類別，保底是下限而非上限 |
| 單顆 OSD 下線・低壓力 | 使用者面三者等效；**回填吞吐應 `high_recovery_ops` ≥ `balanced` ≈ `high_client_ops`** | 低壓力下 client 用不完資源，修復可以取用剩餘 |
| 單顆 OSD 下線・中壓力 | `high_recovery_ops` 的使用者延遲代價應明顯，另兩者相近 | 保底開始咬合 |
| 單顆 OSD 下線・不限速 | **延遲劣化應完整分離，`high_client_ops` 最輕、`high_recovery_ops` 最重，使用者吞吐約按 0.6 : 0.5 : 0.3 分配；修復時間則相反，`high_recovery_ops` 最快** | 資源完全飽和，保底份額應直接映射成吞吐比例 |
| 機櫃隔離・不限速 | **這應是全矩陣分離最大的區塊**；`high_client_ops` 保護使用者最好但修復最慢 | 兩顆 OSD 同時失效，修復量最大 |
| 反覆上下線 | 最長停頓三者等效（由 peering 主導）；**延遲分離應小於同壓力的單顆 OSD 下線** | 卡頓來自 peering 而非資源競爭，排程器插不上手 |
| 整台 node 隔離 | 對齊下線時間後應與單顆 OSD 下線中壓力無異 | 影響範圍相同，只是路徑不同 |
| 循序流量競爭 | 六格應全部等效 | 大 I/O 的成本模型若正確，profile 不該改變結果 |
| 混沌注入 | 累計停頓由少到多為 `high_client_ops`、`balanced`、`high_recovery_ops` | 同不限速的推理 |

上表這些預測底下還有一個共同的源頭，值得單獨拉出來，因為它是整個 campaign 唯一一個給了數字、而不只是給方向的預測。

保底份額要咬合，前提是使用者流量真的逼近那個份額。所以開跑前我們推導了一個換算：把cluster 天花板拆到每顆 OSD 頭上，除以該顆鎖定的容量，得到一個係數；係數再乘上壓力等級，就是「這顆 OSD 的使用者流量佔它名義容量的比例」。這個比例跨過某個 profile 的保底，那個 profile 才會開始限流。

代入校準後的數字，係數是 63,634 ÷ (8 × 6,439) = **1.235**：

| 壓力 | 佔天花板 | 換算後的需求比 | 事前預測 |
|---|---|---|---|
| 低 | 0.25 | 0.31 | 只有 `high_recovery_ops` 劣化，另兩者等效 |
| 中 | 0.50 | **0.62** | **三個 profile 完整分離，服務比例接近保底比例** |
| 高 | 0.80 | **0.99** | 同上 |
| 不限速 | 1.00 | **1.24** | 同上 |

同時凍結的還有它的推翻條件：**需求比 ≥ 0.6 卻量到三者等效，就代表這個換算式漏了項。**

順帶一提，這個係數大於 1 這件事本身就是 §2.2 的量化形式：八顆 OSD 的鎖定容量加起來是 51,512，而 cluster 實際跑出來的天花板是 63,634。我們鎖進去的容量，加總起來比 cluster 自己證明做得到的還少。

一筆誠實的帳：這些預測寫在計畫文件層級，是「區塊」粒度而非「每一格」粒度，每次執行的紀錄檔裡，逐格的預期欄位是空的。這是這次實驗的一項證據債。下次應該在每一格開跑前把該格的預測數值也寫進紀錄檔，而不是只留在計畫裡。

# §4 讀結果之前：三個外表乾淨卻會騙人的資料陷阱

資料集的品質稽核結果是 156 筆全部乾淨、零筆污染、零筆重複。這個數字很漂亮，但**乾淨不等於可用**。

以下三件事，自動化檢查全部沒抓到，每一筆的驗證狀態都是正常。如果你直接對結果目錄跑統計，就會踩到。這也是為什麼這一節排在結果之前，它是讀懂後面表格的前提，不是免責聲明。

## 4.1 一筆分母壞掉的資料，必須排除

延遲惡化倍率的算法是「故障期間 ÷ 注入之前」。分母壞掉，比值就沒有意義。

機櫃隔離、4K、低壓力、`balanced` 這一格的第二次執行，注入前那 60 秒的 p99 延遲量到 28.967 毫秒。同一批 4K 低壓力測試（32 次執行）的中位數是 2.376 毫秒，這一筆高了 12.2 倍。

結果是它的延遲惡化倍率被壓成 0.48，而同一格其他重跑是 5.66。看起來像是「故障期間反而變快」，實際上只是分母被灌水。

推測的成因是 fio 暖機期間的樣本落進了那 60 秒窗。發生率很低：它所屬的那組共 32 次執行只出了這一筆，而監看期間每兩小時掃一次、掃過 155 筆，也只抓到這一筆。

偵測方法很簡單，建議直接做進未來的流程：對每一組（形態 × 壓力）取出所有執行的注入前窗 p99，偏離該組中位數 50% 以上的就當離群，人工複查。

這一筆已從本報告所有統計中排除。

## 4.2 觀測上限決定了被截斷格子的數字

「反覆上下線」這個故障從來沒有自己解除過，OSD 一直在掉線又回來，PG 永遠回不到全乾淨。所以每一次都是撞到觀測上限才收工。

問題在於，這批測試的上限不一致。救援重跑的時候把上限從 2700 秒放寬到 5400 秒，於是：

| 觀測上限 | 筆數 | 延遲惡化倍率 | 中位數 |
|---|---|---|---|
| 2700 秒 | 6 | 3.09 / 3.71 / 4.56 / 4.63 / 4.80 / 4.99 | 4.60 |
| 5400 秒 | 2 | 11.98 / 12.13 | 12.06 |

看起來差了 2.6 倍，但那不是 profile 造成的，是觀測時間造成的。

機制很直白：累計型的指標（例如總劣化秒數）幾乎正比於觀測上限，實測「總劣化秒數 ÷ 上限」穩定落在 0.78 到 0.86 之間。故障既然不會自己好，你量多久就壞多久——這種指標量的是「你看了多久」，不是「cluster 有多糟」。

所以跨上限的數字絕對不能合併平均。這也再次否證了先前在反覆上下線這一組看到的 profile 差異：那些差距有一部分根本就是上限不同造成的。

好消息是有一個指標不受影響。最長停頓時間是上限不變量：上限 2700 秒時量到 21～28 秒，上限 5400 秒時量到 22～24 秒，兩者重疊。被截斷的測試格應該改用它來比較。

## 4.3 「機櫃隔離注入時間差過大」是假警報

這是整個 campaign 裡污染標記的第一名，總共 14 次。

自動化檢查認為：隔離一個機櫃的兩顆 OSD，動作之間如果差超過 5 秒，就不算「同時失效」，資料要作廢。實測量到的差距固定是 7 秒，於是一路報警。

追下去發現是量錯範圍。程式從第一台機器準備防火牆規則之前算到第二台機器掛上規則之後，中間涵蓋了四次 SSH 往返；但真正造成隔離的只有中間那兩次。Azure 上每次 SSH 大約 1.75 秒，四次剛好 7 秒——歷史上四次全部剛好是 7 秒，這是確定性的往返時間，不是抖動。

而 Ceph 自己的紀錄顯示兩顆 OSD 幾乎是同時失效的。下線的版本編號只差 1 到 2 號，換算成時間遠短於檢查認定的 7 秒：

| 注入時間 | 檢查算出的差距 | 第一顆 OSD 下線版本 | 第二顆 | 實際差距 |
|---|---|---|---|---|
| 07-28 07:28 | 7 秒 | 966 | 968 | 2 |
| 07-28 07:59 | 7 秒 | 1364 | 1366 | 2 |
| 08-01 03:58 | 7 秒 | 11806 | 11808 | 2 |
| 08-01 05:30 | 7 秒 | 12185 | 12186 | 1 |

不澄清這一點，就會不當作廢整批機櫃隔離與 node 隔離的資料。

這個缺陷沒有修，是刻意的決定：它不會阻擋測試完成，而在 campaign 進行到一半去改注入路徑，風險高於收益。記錄在案比手癢去改更安全。

# §5 主結果：可以乾淨比較的八組，沒有一組分得出差別

先把可比較的範圍講清楚。十二組故障測試裡三個 profile 都有至少兩筆資料，但其中四組（三個反覆上下線、加上循序不限速）混用了不同的觀測上限，依照 §4.2 自己訂下的規則，這四組不能合併比較。剩下八組觀測條件完全一致，是本節的分析對象。

先看這八組裡證據最強的一組。

「單顆 OSD 下線、4K 隨機讀寫、低壓力」是整個 campaign 樣本最多的情境，而且三個 profile 的每一筆都跑在同樣的 2700 秒觀測上限內、沒有一筆因超時被截斷、也沒有一筆被標記為污染。這裡沒有任何可以拿來解釋差異的雜訊來源。

| profile | 各次的修復完成時間 | 中位數 | 組內全距 |
|---|---|---|---|
| `balanced` | 671 / 759 / 889 秒 | 759 | **218** |
| `high_client_ops` | 796 / 835 秒 | 815.5 | 39 |
| `high_recovery_ops` | 720 / 751 / 787 秒 | 751 | 67 |

三個中位數彼此相差 8 到 64.5 秒。balanced 自己重跑三次的落差是 218 秒。**同一個設定的重跑波動，比三個設定之間的差距還大三倍以上。**

另外兩個指標同樣重疊：延遲惡化倍率落在 3.52 到 3.95 之間，最長停頓 20 到 22 秒，三個 profile 的區間彼此完全罩住，看不出誰比較好。

真正說服我們的不是這一組，是八組全都是這個型態。而且每一次的劇本都一樣：樣本少的時候看起來有訊號，補到第三筆就沒了。

| 一度以為看到的 | 補樣本之後 |
|---|---|
| 修復時間上 `high_recovery_ops` 明顯較快 | `balanced` 第三次跑出 671 秒，比 `high_recovery_ops` 最快的 720 秒還快 |
| 機櫃隔離時三個 profile 的吞吐達成率排序清楚 | `high_client_ops` 第二筆掉到 0.783（前一筆 1.027），自己組內差 0.244，比組間最大差距 0.171 還大 |
| 整台 node 隔離時 `high_recovery_ops` 的延遲代價最大 | `balanced` 補到兩筆變成 7.32 / 8.94，兩組完全重疊 |

## 5.1 那四個越過門檻的比較

嚴格說，整個 campaign 有四次比較越過了事前登記的門檻。它們全部集中在兩個測試格、全部只有兩個樣本，而且兩組的數值範圍都互相重疊。其中兩次還出自反覆上下線，而那一組因為混用觀測上限，本來就不在可乾淨比較的範圍內。

| 比較 | 差距 | 門檻 | 判定 |
|---|---|---|---|
| 反覆上下線（中壓力）最長停頓：`balanced` 對 `high_recovery_ops` | 2.0 秒 | 2.0 秒 | 剛好壓線，樣本不足，且該組不可乾淨比較 |
| 反覆上下線（中壓力）最長停頓：`high_client_ops` 對 `high_recovery_ops` | 2.5 秒 | 2.0 秒 | 樣本不足，且該組不可乾淨比較 |
| 循序流量競爭（中壓力）回填吞吐：`balanced` 對 `high_client_ops` | 106.4 MB/s | 97.1 | 樣本不足 |
| 循序流量競爭（中壓力）回填吞吐：`balanced` 對 `high_recovery_ops` | 126.1 MB/s | 99.6 | 樣本不足 |

後兩筆的原始數字說明了為什麼不能當真：`balanced` 的兩次是 196.4 和 474.3 MB/s，`high_client_ops` 是 360.9 和 522.5，`high_recovery_ops` 是 343.2 和 579.9。三組的範圍彼此重疊得一塌糊塗，平均值的差距只是兩個高變異樣本碰巧落在不同位置。

修復完成時間則是一次都沒有越過門檻。

## 5.2 事前預測幾乎全軍覆沒

| 區塊 | 預測 | 實際發生 | |
|---|---|---|---|
| 穩態對照 | 三者等效 | 三者等效（吞吐差 0.03～1.58%） | ✔ 命中 |
| 單顆 OSD 下線・低壓力 | 回填吞吐應是 `high_recovery_ops` 最快 | **實際最快的是 `balanced` 641.4，其次 `high_client_ops` 597.8，最慢 `high_recovery_ops` 565.9 MB/s，完全反過來** | ✘ 推翻 |
| 單顆 OSD 下線・不限速 | 修復時間應是 `high_recovery_ops` 最快、`high_client_ops` 最慢 | **實際最快的是 `high_client_ops` 953.5 秒，最慢的是 `balanced` 971.5 秒，順序相反** | ✘ 推翻 |
| 機櫃隔離・不限速 | 分離最大，C 修復最慢 | 修復時間 1325.5 / 1269 / 1283 秒，**C 反而最快**；分離也不是最大 | ✘ 推翻 |
| 反覆上下線 | 延遲分離**小於**單顆 OSD 下線 | 故障窗 p99 最大差距 **92.3 毫秒**，而同壓力單顆 OSD 下線只有 **1.9 毫秒**——大了 48 倍 | ✘ 推翻 |
| 反覆上下線 | 最長停頓三者等效 | 平均 23 / 23.5 / 21 秒，範圍 [21,25] / [22,25] / [20,22] 互相重疊 | ✔ 命中 |
| 循序流量競爭 | 六格全部等效 | 兩筆越過門檻，但樣本不足且範圍重疊（§5.1） | ～ 大致成立 |
| 混沌注入 | 累計停頓 `high_client_ops` 最少、`high_recovery_ops` 最多 | 無資料可檢驗（§9） | ✘ 無法檢驗 |

> 反覆上下線那兩列用的是觀測上限 2700 秒的子集（各 profile 兩筆），不含上限 5400 秒的救援重跑。混著算會落入 §4.2 的陷阱。

上表之外還有一條，就是 §3.1 那個唯一給了數字的預測。中壓、高壓、不限速三檔的需求比分別是 0.62、0.99、1.24，全部落在「應該完整分離」的分支，而實際全部等效——**它自己事前凍結的推翻條件成立了。**

這一條比上表任何一列都重。上表推翻的是方向，這一條推翻的是我們對「mClock 在這套系統裡到底怎麼運作」的整個算式。漏掉的是什麼，就是 §5.4 的主題。

**看得出一個很不舒服的規律：所有預測「會有方向性差異」的都被推翻，唯二命中的兩條，預測的都是「不會有差別」。**

反覆上下線那一條尤其值得記住。我們預期 peering 主導、排程器插不上手、所以分離應該最小；結果它是全矩陣分離最大的地方（雖然如 §4.2 所述，那個數字有一部分是觀測上限造成的假象）。推理很合理，方向完全錯誤。這是不做實驗就不會知道的事。

反覆上下線根本是另一個量級的災難。不必理會倍率（§7 會說明倍率為什麼會騙人），直接比絕對值就好：乾脆掉一顆 OSD 的時候，使用者的 p99 落在 8.5 到 13 毫秒；OSD 反覆上下線的時候是 304 到 1,585 毫秒。**絕對延遲差了三十到一百二十倍。** 而且乾脆下線大約十二分鐘就修復完成，反覆上下線在整個 campaign 裡從來沒有自己結束過。

那三列甚至還是下限。同樣的中壓力情境，觀測 45 分鐘量到 p99 304～472 毫秒，觀測 90 分鐘量到 617～1,485 毫秒；故障不會結束，所以你量多久就壞多久（§4.2）。真實世界裡沒有人會在 45 分鐘後停止計時，真正的數字只會更難看。

相對地，最長停頓穩定得出奇。不論哪種故障、哪種壓力、哪個 profile，全部落在 20 到 28 秒之間。這是整份報告最一致的觀測，也是唯一夠格拿去訂 timeout 門檻的數字。

> 這對營運的意義比選 profile 大得多。與其煩惱故障當下要切哪個 profile，不如確保壞掉的 OSD 會乾脆地被標記下線。差別是「痛 3.7 倍、十二分鐘結束」對上「痛三十倍以上、不會結束」。

## 5.4 為什麼分不出來：三個比「cluster 太小」更近的解釋

分不出來是量測事實。但「為什麼分不出來」是另一個問題，而最容易脫口而出的答案是：cluster 太小，mClock 還沒被逼到會咬合的位置。

那個答案可能對，但它不是最近的那一個。至少有三件事，在 mClock 有機會發揮之前就先擋住了它。三件都不需要換一套更大的 cluster 才看得到，而且三件都在我們自己的設定裡。

**第一，mClock 管不到副本寫入。**

一個使用者的寫入進到 Ceph，會變成三個動作：主副本 OSD 自己寫一份，再轉發兩份給另外兩顆 OSD。mClock 只把第一種算進「使用者流量」這一類。後面那兩份轉發過來的請求，在原始碼裡走的是一條叫 `immediate` 的特快通道，直接跳過整個排程器。

代回 §2.2 那張拆解表：每顆 OSD 每秒處理的 12,727 個動作裡，有 4,773 個——**37.5%**——根本不在 mClock 的帳上。排程器是在一個被切掉三分之一的分母上分配份額，而被切掉的那部分照樣在吃磁碟和 CPU。

寫入比例越高這個效應越強。純寫入的循序測試裡，繞過排程器的比例會到三分之二。

**第二，校準後的容量偏低，保底從來沒有真的緊繃過。**

三個 profile 的保底加起來都剛好是 100%：balanced 是 50 + 50，`high_client_ops` 是 60 + 40，`high_recovery_ops` 是 30 + 70。100% 的什麼？就是鎖定的那個容量值，每顆 6,439。

但 §2.2 已經算出來，這顆 OSD 實際做得到大約 12,700。也就是說，**不管選哪個 profile，兩邊的保底都能同時輕鬆滿足，還剩一半的能力沒分配出去。** 保底是三個 profile 差最多的地方，而它在整個 campaign 裡從來沒有變成真正的限制。

這裡有一個很不舒服的推論：如果當初不校準、沿用 21,500，保底總和會變成實際能力的 1.7 倍，也就是超額認購——**那反而會逼出 profile 之間的差別。** 我們為了嚴謹而做的校準動作，有可能正好抹掉了要測的東西。

這是推論，不是實測。要驗證得有一組把容量設在不同值的對照臂，而 campaign 從頭到尾只跑了鎖定值這一組。

**第三，修復的併發度被另一個參數卡死。**

Ceph 在 mClock 模式下會強制把「同時進行的 backfill 數量」設成 1。這是排程器之外的另一道閘門：修復流量還沒排到 mClock 面前，就先被這道閘門掐住了。

份額只有在「兩邊都想要更多」的時候才有意義。如果修復這一邊根本產不出足夠的請求來競爭，那 40% 和 70% 的保底就沒有差別——不是排程器不管用，是它沒有東西可管。

這一條在開跑前的假說文件裡就寫好了處置方式：三個 profile 若無法區分，報告必須註明「上限參數在這個拓撲下不可觀測」。這裡補上。

**三條合起來**的意思是：「換一套更大的 cluster 就分得出來了嗎」可能問錯了方向。更該先問的是「在這個配置下，mClock 到底管得到多少工作」。答案是：管得到大約六成的請求，而且在它管得到的那六成裡，份額從來沒有真的緊繃過。

沒有一條推翻 §5 的結果。它們改變的是這個結果該怎麼讀，而那正是下一節的事。

## 5.5 結論怎麼寫才誠實

在這個 cluster 規模、這個配置與這個樣本數下，**修復完成時間、延遲惡化倍率、最長停頓這三個指標都不具備區分 profile 的能力。**

這句話的重點在於它不是「我們沒測到」，而是八組乾淨的比較，一組都沒有測到，而且每次以為測到，都被下一筆資料推翻。硬湊一個 profile 排名出來，只會被下一個補到第三筆的人推翻，這件事我們已經自己做過好幾次了。

但同樣不能寫成「mClock profile 沒有用」。加上 §5.4 之後，最誠實的一句是：**在這個配置下，三個 profile 沒有機會表現出差別。** 「工具在這個配置下沒有作用」跟「工具沒有作用」是兩句話，而這次的實驗只證明得了前面那句。

# §6 唯一存活的線索：不限速時的吞吐達成率

有一個指標在一個特定情境下表現得完全不同。

吞吐達成率指的是故障處理完之後，重新量到的 4K 吞吐相對於校準天花板（63,634 IOPS）的比例。在「單顆 OSD 下線 + 4K + 不限速」這一格：

| profile | n | 各次的值 | 平均 | 組內全距 |
|---|---|---|---|---|
| `high_client_ops` | 3 | 1.0247 / 1.0250 / **1.0009** | 1.017 | 0.0241 |
| `balanced` | 2 | 0.9042 / 0.9064 | 0.905 | 0.0023 |
| `high_recovery_ops` | 2 | 0.8822 / 0.8840 | 0.883 | 0.0018 |

**三組的數值範圍完全不重疊**——`high_client_ops` 最低的 1.0009 仍高於 `balanced` 最高的 0.9064，`balanced` 最低的 0.9042 仍高於 `high_recovery_ops` 最高的 0.8840。組間差距是組內波動的 4.6 到 9.7 倍。

> 這個比值的算法是「兩組平均值之差 ÷ 兩組之中較大的那個組內全距」。三組兩兩相比分別得到 4.64（`high_client_ops` 對 `balanced`）、5.56（`high_client_ops` 對 `high_recovery_ops`）、9.70（`balanced` 對 `high_recovery_ops`）。上表的全距是用未四捨五入的原始值算的，所以拿表上四位小數自己減會有末位差異。

而且排序完全符合 mClock 的設計意圖：偏袒使用者流量的 profile 保住了最高的吞吐，偏袒修復的 profile 讓得最多，預設值在中間。這是整個 campaign 唯一一次，理論預測與觀測方向一致且乾淨可分。

## 6.1 為什麼它還是不能拿去上線

四個理由，每一個單獨都足夠：

1. 它不是事前登記的主要指標。沒有預先設定的門檻、沒有事前的檢定計畫。事後才挑出來的指標，天生就有挑選偏誤。
2. 樣本仍然太少（兩到三筆）。
3. 同一個指標在機櫃隔離情境下不成立。那一組 `high_client_ops` 自己組內就差 0.244，比三組之間最大的 0.187 還大。**只有單顆 OSD 下線這一組能保留。**
4. 它量的是「事後」不是「當下」。這是故障處理完之後重測的吞吐，不是使用者在故障當下的體感。

## 6.2 一個很有說服力的巧合

這個訊號最初被記錄下來的時候只有兩筆：1.0247 和 1.0250，組內全距只有 0.0003，組間是組內的 10 到 70 倍。看起來強得不像話。

收官對帳時，我們在資料裡找到一筆兩份中期報告都沒有納入的第三次執行。它狀態完全乾淨——正常完成、未被污染、未被截斷、觀測上限相同——只是漏算了。它的值是 1.0009。

加進去之後，組內全距從 0.0003 變成 0.0241，放大了 80 倍；組間對組內的比值從「10 到 70 倍」掉到「4.6 到 9.7 倍」。

**訊號活下來了，但削掉一大截。** 而這正是 §5 那條教訓的最後一次示範——連整個 campaign 唯一的正面結果，都在收官前一刻被第三筆資料咬了一口。

這就是為什麼這份報告不用兩個樣本下任何結論。

# §7 為什麼不能跨壓力比較

延遲惡化倍率有一個很容易誤用的性質：它是比值，而分母隨壓力等級劇烈變化。

同樣是機櫃隔離，倍率在不同壓力下是這樣的：

| 壓力 | 延遲惡化倍率 | 注入前的 p99（分母） |
|---|---|---|
| 4K 低壓力 | 5.7 ～ 6.2 | 約 2.4 毫秒 |
| 4K 中壓力 | 5.6 ～ 8.2 | — |
| 4K 不限速 | **1.4** | 約 52 毫秒 |

不限速那一檔看起來「幾乎沒受影響」，但那是假象：分母本來就已經很大了。系統在不限速時本來就跑在延遲的懸崖邊，故障造成的絕對衝擊被巨大的分母壓平。循序不限速的分母更誇張，約 105 毫秒。

反方向也一樣極端：反覆上下線在 4K 低壓力下，分母只有 2.4 毫秒，倍率直接爆到 313 到 476。

**同一個故障，在不同壓力下的比值差兩個數量級。**

所以：不限速與循序這兩個區間，應該改看絕對值（最長停頓秒數、總劣化秒數），而不是倍率。跨壓力等級直接比倍率，會得出完全相反的結論。

# 第二部：這種實驗要怎麼做才不會白做

這一部跟 mClock 無關。它記錄的是量測架構本身的失敗，對下一個要做故障注入實驗的人（包括未來的我們自己）比 profile 結論更有用。

# §8 有效性檢查：六次假警報、零真陽性

我們設了一道自動檢查，用來偵測「機器狀態隨時間漂移」：如果今天的基準比歷史同條件的中位數差太多，就停下佇列等人來看。

**八天之內它擋下佇列六次。六次全部是假警報，一次真陽性都沒有。**

每次的根因都不一樣：

| 第幾次 | 到底哪裡錯了 |
|---|---|
| 1、2 | 校準的時候沒有取樣程式在跑。拿來當基準的那批資料，量測條件跟實測根本不是同一回事 |
| 3 | 新組合才跑三次就開始判漂移，樣本根本不夠 |
| 4 | 參考池把不同故障型態混在一起比，等於拿蘋果比橘子 |
| 5 | 全體共用一個門檻，但每種組合本來的正常離散度天差地遠，粗門檻抓不到細異常 |
| 6 | 算「連續超標幾次」的時候又回頭用全體共用的計數，沒有照組合分開算 |
| 7 | 一個本來只看絕對值的檢查，被拿去累計「連續漂移」，語意根本對不上 |

六次的錯法都不一樣，但骨子裡是同一件事：**判準的某個維度，沒有跟著資料的實際結構走。**

門檻數值從頭到尾沒有調過一次。容忍度 0.15、離散度乘數 3.0、達成率下限 0.85、連續次數 3，全部是原始值。六次修的都是「同條件」怎麼定義，不是數字大小。

## 8.1 最根本的一條：它量錯了東西

這道檢查用的是故障處理完之後的重測值。而那個值本身就極度不穩定：修復尾段的離散度高達 29.2%，最大最小值差 8.5 倍。拿一把會自己抖動 8 倍的尺去量漂移，當然一直誤報。

而更好的儀器就在旁邊。每一次執行注入之前那 60 秒窗，跨八天、在八個不同組合上，離散度只有 1.1% 到 9.5%。

同一份資料裡就躺著一把穩定得多的尺，只是沒被拿來用。

## 8.2 可以帶走的通則

> 以「歷史同條件中位數」為基準的漂移檢查，**失敗模式集中在「同條件」的定義，不在門檻數值。**
>
> 設計的時候應該先窮舉所有會讓量測條件系統性偏移的變因，再決定要分幾層；而不是先訂一個門檻，等它報警了再回頭補分層。

最終的處置是：漂移檢查改為只告警、不停佇列。判定邏輯與所有資料有效性檢查一律不動，訊號照常記錄下來供事後稽核。降低誤報的成本，但不減少證據。

# §9 混沌注入在這套量測架構下不可驗證

三個混沌測試格，零筆數值資料。原因不是 cluster 撐不住，是量測工具自己被打掛了。

覆蓋率打卡的統計說明了一切：

| | 混沌注入 | 一般故障型態 |
|---|---|---|
| 涵蓋秒數 | 約 1826 | 約 1800 |
| 缺口 / 缺口秒數 | 0 / 0 | 0 / 0 |
| 無法佐證的秒數 | **547 / 592 / 608（約 33%）** | 9 ～ 10 |

差了 55 到 68 倍。

成因很直接。混沌注入在 30 分鐘內打了 44 個事件，反覆隔離多台機器；而覆蓋率監看程式是靠 SSH 進去打卡的，於是它的打卡路徑正好被自己注入的故障切斷，每次斷 60 到 90 秒。

**資料其實是完整的，缺口為零；壞掉的是「證明資料完整」的那份證據。** 但因為證據不足，三個測試格乘以三次嘗試全部被標記污染，統計檔案從未產生。

這是「被測系統的故障會反過來干擾量測工具」的極端版本，指向一個很明確的改進方向：覆蓋率打卡不該依賴會被故障影響的路徑。

另外還有一個尚未修的程式缺陷：混沌注入寫入的時間戳欄位名稱與統計程式讀取的不一致，會導致統計走錯分支。在任何混沌測試重跑之前，這兩件事都必須先修。

---

# §10 監看程式分不出「死了」和「刻意停手」

佇列有一個監看程式，負責在佇列意外死掉時把它拉起來。舊版只用「行程還在不在」來判斷。

問題是，佇列被 §8 那道檢查刻意停下的時候，行程也不在。於是監看程式每兩分鐘把它拉起來一次，佇列一起來就再度自我停止——空轉 40 次、43 分鐘，直到撞上重啟次數上限才罷手。

修正後在真實環境驗證通過：偵測到「刻意停手」狀態就留言收工，重啟次數 0。

順帶抓到一個更難查的方向：舊版比對行程名稱的方式，會誤匹配到靜態檢查工具正在檢查那個腳本的行程。而靜態檢查每次測試前都會跑——也就是說，**佇列真的死掉的時候，監看程式反而可能一路睡下去。** 這是比誤判「刻意停手」更危險的失敗模式。

# §11 為什麼 campaign 不會自然收斂

排程器有一個自動補樣本的機制：某個測試格的變異係數超標，就要求多跑幾次，上限五次。設計意圖是「不夠穩就多量幾次」。

但這些格子的高變異是物理性的，補樣本不會讓它變小。於是負回饋失效：變異大 → 要求補樣本 → 補完變異還是大 → 繼續要求。

實測的樣子是這樣：待辦數量連續七次檢查都停在 17。八小時內完成了 5 次執行，同時新增了 5 次補樣本要求，淨進度為零。

這本身就是一條方法論教訓：

> **以變異係數為觸發條件的自動補樣本機制，遇到本質上高變異的量，會無限要求下去。**
>
> 必須另外設一個絕對上限，或是在偵測到「補了樣本變異沒下降」時改為回報而非續補。

這也是為什麼 campaign 在此停手是一個決定，而不是一個終點。它不會自己結束。

## 11.1 環境雜訊（順帶說明部分污染標記）

中斷前的日誌出現過 SSH 連線逾時與網路不可達。網路瞬斷造成覆蓋率監看程式少打一次卡（25 秒），於是那次執行被判定證據不足。

檢查的判斷是正確的（證據確實缺了一段），但成因是無害的雲端網路抖動，不是量測缺陷。記在這裡，避免未來把這類標記誤讀成資料有問題。

## 12.1 前四條該怎麼執行

**第 1 條，維持預設。** 八組觀測條件一致的故障測試裡，組內變異都大於或等於組間差異，修復完成時間更是一次都沒有越過事前登記的門檻。適用條件是八顆 OSD、本機 NVMe、每格兩到三個樣本。換一個規模要重測。

**第 2 條，容量參數。** 值要逐顆設，因為八顆各不相同（本次是 6,057 到 6,646 IOPS，變異係數 3.19%）；同時要關掉開機自動重測，否則重開機就會被蓋回去：

```bash
# 對每一顆 OSD 各做一次，<value> 換成該顆的值
ceph config set osd.<id> osd_mclock_max_capacity_iops_ssd <value>
ceph config set osd.<id> osd_mclock_skip_benchmark true

# 設完回讀確認，這兩個值都必須跟你設的一致
ceph config show osd.<id> | grep -E 'max_capacity_iops_ssd|skip_benchmark'
```

值從哪裡來，這次的經驗是：**別直接抄開機測試的結果，那是低估。** 它只跑了 0.47 秒、單執行緒、不經過網路和副本複製（§2.2）。比較實際的做法是拿一個真實負載壓到飽，把 cluster 吞吐拆回每顆 OSD，用那個數字。

這條標成「推論」而不是「實測」，因為 campaign 從頭到尾只跑了一組容量值，沒有對照臂，所以講不出校準到底值多少。更麻煩的是 §5.4 第二點：鎖一個偏低的值，可能反而讓 profile 的差異消失。**方向上「別停在 21,500」是對的，但「該設多少」這次沒有答案，這是下一輪要測的東西。**

**第 3 條，別讓 OSD 反覆上下線。** 效果量在整份報告裡最大：乾脆下線時使用者 p99 是 8.5～13 毫秒、約十二分鐘結束；反覆上下線是 304～1,585 毫秒、而且不會結束。

這一條的做法跟直覺相反——你多半不需要「加上」限制，因為它已經在了。cephadm 佈署的 OSD systemd unit 預設帶著 `StartLimitInterval=30min` 與 `StartLimitBurst=5`：同一顆 OSD 在 30 分鐘內第 5 次啟動之後，systemd 就會拒絕再拉起它，並把 unit 標成 `failed (Result: start-limit-hit)`。

所以真正要做的是監控這件事有沒有發生。OSD 被 systemd 放棄之後，它就只是一顆安靜的死 OSD，Ceph 的健康摘要不一定會明顯指出「這是被重啟保護擋下來的」。請針對 `start-limit-hit` 這個狀態獨立設告警，不要只看 Ceph health。同時檢查 `mon_osd_down_out_interval` 有沒有長到讓壞掉的 OSD 一直卡在 down 但沒 out 的狀態。

> 附帶一提，這也解釋了本實驗的反覆上下線為什麼從未自行結束：它是用網路層隔離與手動標記做出來的，並沒有真的反覆重啟 OSD 服務，所以永遠碰不到這個上限。真實環境若是 daemon 自己一直崩潰重啟，systemd 會在第五次後替你踩煞車——這是本實驗的注入方式與真實故障的一個重要差異。

**第 4 條，VM 內的磁碟逾時。** 這條標為推論，因為我們沒有實際測試 VM 內的行為。但觀測到的最長停頓穩定落在 20 到 28 秒，而 Linux 的 SCSI 磁碟預設逾時是 30 秒，餘裕只剩兩到十秒。建議提高到 60 秒：

```bash
# 在 VM 內執行，<dev> 換成實際裝置（如 sda）
echo 60 > /sys/block/<dev>/device/timeout
```

這個設定重開機後會消失，要長期生效得寫進 udev 規則。使用 virtio-blk 而非 SCSI 的 VM 沒有這個設定，需要改從應用層的重試邏輯著手。上線前請在你自己的環境驗證這個門檻。

## 12.2 最該帶走的不是答案，是副產品

這是整份報告最反直覺的地方。我們花 230 小時想知道「該切哪個 profile」，答案是「切了也沒用」。

但同一批資料指出了三件更值得帶走的東西，而且一件比一件不像答案。

**能立刻照做的只有一條，就是第 3 條：別讓 OSD 反覆上下線。** 這是整份報告唯一直接量到、效果量又壓倒性的發現——乾脆下線是痛 3.7 倍、十二分鐘結束；反覆上下線是痛三十倍以上，而且不會結束。

**第二條是一個沒答完的題目。** 容量參數的方向很清楚（別停在編譯預設值），但「該設多少」這次沒有答案：開機自動測試低估一半，編譯預設值高估兩三倍，而這兩個方向會把保底總和推到實際能力的兩側。這條的正確定位是下一輪實驗的第一個題目，不是立刻照做的處方。

**第三條根本不是建議，是一個提醒。** 我們花了 230 小時去比三個 profile，卻在收官複查時才發現：mClock 在這個配置下管不到大部分的工作（§5.4）。也就是說，這個實驗有很大一部分是在量一個沒有被啟動的機制。任何想重做的人，應該先確認那三件事，再開機器。

# §13 限制：哪些綁這個環境，哪些是機制層級

限制分兩種，要分開看：一種是「換個環境結論就不成立」，一種是「這次的配置讓實驗本身沒問到該問的問題」。第二種比第一種嚴重，先講。

**配置層面的限制（§5.4 展開）。** mClock 在這次的設定下管不到副本寫入、保底份額從來沒緊繃過、修復的併發度被另一個參數卡死。這三件事都不是規模造成的，換一套一樣配置的大 cluster 也照樣存在。任何要重做這個實驗的人，這三條要先處理掉。

**環境層面的限制。** cluster 小：八顆 OSD、每台一顆，修復一顆只需要在剩下七顆之間搬資料；在幾百顆 OSD 的 cluster 上，份額很可能在完全不同的位置咬合。而且樣本數普遍只有兩到三筆。機櫃是合成的：同一張網卡、同一個子網路，用防火牆規則做出來，不能拿來推論真正的跨可用區網路故障——真實跨區故障有頻寬、延遲、封包遺失，這裡一項都沒有。磁碟是本機 NVMe：換成 SATA SSD 或機械硬碟，資源競爭的形態會完全改變。

**可以帶走的，都是跟被測系統無關的部分。** 容量參數不該停在編譯預設值（§2.2），這是 mClock 的算術基礎，跟規模無關——但「該設多少」這次沒答出來。累計型指標會被觀測窗長度污染（§4.2）、比值型指標在分母大的區間會失去解析度（§7），這兩條是量測學，跟 Ceph 無關。第二部那四條方法論教訓（§8～§11）講的是實驗架構本身的失敗模式，換個系統照樣成立。

最後一件必須說清楚的事。**本報告沒有證明三個 profile 相等**，它證明的是「在這個規模、這個配置、這個樣本數下，用這三個指標區分不出來」。我們沒有做等價性檢定，也沒有給信賴區間。這兩句話不一樣，不要簡化成前者。

# §14 未解問題與下一步

1. **容量參數該設多少？**（§2.2、§5.4）開機自動測試低估、編譯預設值又跟硬體無關，兩者把保底總和分別推到實際能力的一半與 1.7 倍——剛好落在天平兩側。要答就得有對照臂：同一組故障，容量分別設在偏低、貼近實測、偏高三個值，看 profile 的分離度怎麼變。這一題不先答，重跑幾次故障矩陣都可能是白跑。
2. **mClock 管不到的那 37.5% 能不能量出來？**（§5.4 第一點）需要在故障期間收每顆 OSD 各類佇列的長度組成，直接驗證「特快通道佔了多少」。這次的資料收集沒有涵蓋這個。
3. 吞吐達成率的訊號值不值得追？（§6）它是唯一方向正確且分離乾淨的觀測。要確認需要：把樣本補到五筆以上、事前登記門檻、並確認它在單顆 OSD 下線以外的情境是否成立。附帶一提，依 §5.4 第二點的推理，容量若設得更貼近實測，這個訊號應該只會更明顯而不是更淡——這也是可以順便驗的。
4. 混沌注入必須換一套打卡機制才能測。（§9）覆蓋率證明不能走會被故障切斷的路徑；時間戳欄位名稱不一致的缺陷也要先修。
5. 更大的 cluster 會不會就分得出來了？八顆 OSD 可能根本沒把 mClock 逼到會咬合的位置。這題排在後面而不是最前面，是因為 §5.4 那三個原因不需要換規模就存在——先把它們排除掉，這一題才問得乾淨。
6. 機櫃隔離的注入時間差量測範圍（§4.3）仍是錯的，只是被記錄下來而非修正。下次重構注入路徑時應一併修好。
7. 成本從未與 Azure 實際帳單對帳。（§15）


這幾個數字分兩組讀。「完成／缺件」是互斥的帳，156 + 21 = 177 剛好是規劃總數；「被截斷／污染／待人工」則是標籤，會跟前面那組重疊，不要拿去相加。

- 63 個測試格全部有資料，混沌注入的 3 格除外。
- 污染 0、重複 0。這是資料集品質最重要的兩個數字，但請記得 §4 那三個陷阱都不會反映在這裡。
- 被截斷 24 筆全部出自反覆上下線，屬預期行為（§4.2）。這 24 筆算在「完成」裡，資料可用，只是修復時間要當成下限讀。
- 待人工 7 筆 = 混沌注入的 3 格 + 先前累積的 4 筆。那 4 筆是循序高壓對照組一筆、反覆上下線三筆，全都因為連續三次遭遇污染或中斷而自動跳過。
- 缺件 21 筆 = 混沌注入 3 次 + 另外 18 次執行（分散在多個測試格，是各自的第三或第四次補樣本）。混沌那 3 次同時也掛著待人工的標籤，是同一件事的兩個面向，不是兩筆帳。那些測試格都已經有兩筆資料，補不補都不影響結論。
- 「放棄」為 0，意思是沒有任何一格被正式除名。混沌注入雖然拿不到資料，帳面上仍保留為待處理，沒有從矩陣裡刪掉。

cluster 收工時的狀態是乾淨的：129 個 PG 全部 `active+clean`，8 顆 OSD 全部 up 且 in，沒有殘留的隔離規則。健康狀態顯示兩則警告，來自實驗刻意設定的停用 scrub 旗標及其衍生警告，不是損壞。

| 每顆 OSD 的副本寫入 | 63,634 × 0.3 × 2 ÷ 8 = 4,773 |
| §3.1 的係數 | 63,634 ÷ (8 × 6,439) = 1.235 |

前提有三個，都可在原始碼複驗：讀取只由主副本 OSD 服務；一次寫入產生兩份副本請求；副本請求走 `immediate` 通道，不計入使用者流量這一類（`OpSchedulerItem.h` 的 `PGOpItem::get_scheduler_class`）。PG 在八顆 OSD 上均分（128 PG × 3 副本 ÷ 8 = 每顆 48）。
