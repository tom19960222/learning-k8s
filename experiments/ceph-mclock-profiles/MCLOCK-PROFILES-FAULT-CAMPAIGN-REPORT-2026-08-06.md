# §0 給沒參與的人的三分鐘版本

Ceph 內建三種 mClock scheduler profile，決定 OSD 忙不過來時要優先服務誰：`high_client_ops` 偏袒前台的使用者流量，`high_recovery_ops` 偏袒後台的資料修復，`balanced` 是預設值，兩邊各半。官方文件把該怎麼選講得很清楚，但沒有提供故障情境下的量化幅度——真的壞掉一台機器的時候，換 profile 到底能讓使用者少痛多少？

我們在 Azure 上開了一套八台 NVMe 機器的 Ceph cluster，花了大約 230 小時，對三個 profile 注入同一批故障：拔掉一顆 OSD、隔離整個機櫃、讓 OSD 反覆上下線。量四件事：資料修復完要多久、使用者感受到的延遲惡化幾倍、最長卡住不動幾秒、故障期間還跑得到多少吞吐。

**結論是：用這些指標與現有樣本，沒有得到足以支持故障時切換 profile 的差別。**

這句話有兩個但書，都不能漏。

第一，這是「量不到」，不是「證明相等」。八顆 OSD、本機 NVMe、每格只有兩到三個樣本，我們沒有做等價性檢定（§13）。

第二，**這次沒有證明 mClock 真正遇到可分流的競爭。** 有三個更近的候選原因：部分副本工作走了另一條高優先度路徑、沒有證明使用者 I/O 與修復 I/O 在同一條排程佇列裡持續同時塞車、修復的併發度又被另一個參數卡住（§5.5）。所以最準確的講法是「在這個配置與觀測條件下，沒有看到三個 profile 分開」——而不是「三個 profile 沒有差別」。

我們把「故障型態 × 壓力等級」的每一種組合當成一組來比。十二組裡三個 profile 都拿到至少兩筆資料，其中觀測條件一致、可以比較的有八組。修復時間沒有任何兩兩比較跨過事前門檻；延遲的正式判定也都未達門檻。其他指標只有四次碰到門檻，全部只有兩個樣本且範圍重疊，其中兩次還來自不可合併的反覆上下線組（§5.2）。

最乾淨的一組是「單顆 OSD 下線 + 4K 隨機讀寫 + 低壓力」：三個 profile 的修復時間中位數是 759、815.5、751 秒，彼此最多差 64.5 秒；而光是 balanced 自己跑三次，就從 671 秒橫跨到 889 秒，差了 218 秒。

部分排序在補樣本後改變，剩下的也沒有跨指標形成一致方向。以現有樣本，沒有證據支持故障時切換 profile。

有一項值得追蹤的次要結果：在完全不限速的壓力下拔掉一顆 OSD 時，`high_client_ops` 觀測到較高的使用者吞吐，達成率 1.017，對上 `balanced` 的 0.905 和 `high_recovery_ops` 的 0.883，三組值域沒有重疊，方向符合 mClock 的設計意圖。但它只有兩到三個樣本、不是事前登記的主要指標，而且同一個指標換到「機櫃隔離」情境就不成立。這不足以作為上線切換的理由，只能當下一輪的假說。

所以該做什麼：現階段維持預設的 `balanced`，不因故障切換 profile。真正該動手的是另外兩件事：

- **確保壞掉的 OSD 乾脆下線，不要反覆上下線。** 低壓力下，乾脆掉一顆時 p99 是 8.5～9.6 毫秒，反覆上下線是 734～1,585 毫秒，約為 77～187 倍；中壓力是 10.7～13.0 對 304～472 毫秒，約為 23～44 倍。乾脆下線約十二分鐘修復，反覆上下線則在觀測期間都未完成。不限速時差距縮為 2.6～4.9 倍，因此效果量必須連同壓力條件一起讀。
- **先確認 OSD 容量參數的來源，不要拿不同層級的 IOPS 互填。** 本次有三種數字：raw NVMe 每顆 276,735～304,158、OSD 開機測試每顆 6,057～6,646、RBD fio 整個 cluster 63,634 IOPS。它們的 I/O 路徑、讀寫比例、並行度、時間與統計範圍都不同，不能用倍數判定誰高估或低估，也不能把 raw 或 cluster IOPS 直接寫進 per-OSD 參數（§2.2）。

報告的後半跟 mClock 無關，但大概更有用：這種故障注入實驗本身有幾個會讓你白做工的坑，我們全部踩過了——包括一道八天內誤報七次、真陽性掛零的自動檢查，以及一整組因為「量測工具被自己注入的故障打斷」而沒有產出統計結果的測試。

## 幾個名詞，先講定義

報告正文盡量不用內部代號，但有幾個 Ceph 與統計用語會反覆出現，先講清楚：

- **OSD** — Ceph 裡負責保管資料的常駐程式，一顆磁碟通常對應一個。八台機器各一顆，就是本次的八顆 OSD。
- **PG**（placement group） — Ceph 把資料分成一群一群來管理的單位。「所有 PG 回到 `active+clean`」等於「副本全部補齊、狀態正常」，本報告用它來判定修復完成。
- **backfill** — 一顆 OSD 掛掉後，把缺少的副本重新複製到其他 OSD 的過程，也就是本報告講的「修復」。
- **p99 延遲** — 把所有 I/O 請求的延遲排序後第 99 百分位的值，代表「最慢的那 1% 有多慢」。比平均值更能反映使用者實際的卡頓感受，所以本報告一律看 p99，不看平均。
- **變異係數** — 標準差除以平均值，用來衡量一批數字有多分散，越小代表越一致。本報告用它判斷「同樣的測試重跑幾次，結果穩不穩」。
- **campaign** — 這次橫跨十天、約 230 小時的整批實驗的總稱。
- **OSD shard** — OSD 內部用來平行處理工作的排程分區；同一顆 OSD 的不同 shard 各有自己的佇列。
- **queue class／backlog** — queue class 是 mClock 替 client、recovery 等工作分的排程類別；backlog 表示該類工作已排隊、來不及立刻處理。
- **觀測 gate** — 實驗開跑或判定資料有效前必須通過的檢查，例如 cluster health、設定回讀與量測涵蓋率。

# 第一部：mClock profile 到底有沒有差

# §1 這次在測什麼

## 1.1 為什麼 OSD 需要一個排程器

一顆 OSD 同時要服務兩種完全不同的工作。一種是前台的使用者讀寫，慢了會被立刻感覺到。另一種是後台的資料修復。當一顆 OSD 掛掉，它上面的資料副本數不足，cluster 必須把缺的副本重新複製到別處（backfill），這件事不做完，再壞一顆就會掉資料。

這兩件事搶同一批磁碟和 CPU。修復做得越兇，使用者越痛；修復做得越溫和，暴露在「再壞一顆就完蛋」的時間窗越長。mClock 就是決定這個取捨的排程器。

它給每一類工作三個參數：**reservation**（保底，無論如何都給的最低份額）、**weight**（保底之外，剩餘資源怎麼分）、**limit**（上限，最多不能超過多少）。Ceph 把常用組合包成三個現成的 profile，這樣管理員不必自己調六個數字。

## 1.2 三個 profile 差在哪

以下是 Ceph v19.2.2 實際寫死的值。「client」是使用者流量，「recovery」是資料修復，「best effort」是 scrub 之類的雜項。

| profile | client | recovery | best effort |
|---|---|---|---|
| `balanced`（預設） | 保底 50%，權重 1，無上限 | 保底 50%，權重 1，無上限 | 保底 0%，權重 1，上限 90% |
| `high_client_ops` | 保底 **60%**，權重 **2**，無上限 | 保底 40%，權重 1，無上限 | 保底 0%，權重 1，上限 70% |
| `high_recovery_ops` | 保底 30%，權重 1，無上限 | 保底 **70%**，權重 **2**，無上限 | 保底 0%，權重 1，無上限 |

差距看起來不小：使用者流量的保底份額從 30% 到 60%，差了一倍。直覺上，故障期間切到 `high_client_ops` 應該能讓使用者明顯少痛，代價是修復拖比較久；切到 `high_recovery_ops` 則相反。

這份報告要回答的就是：這個直覺在真實故障下，能量到多大的效果。

三個 profile 都可以在執行中切換，不必重啟 OSD。但「設定送出去」不等於「八顆 OSD 都生效」，所以每次切換之後我們都會逐顆確認，確認不過就不開始測。

## 1.3 為什麼值得花 230 小時

因為文件只告訴你方向，沒告訴你幅度。「偏袒使用者流量」如果實際上只換到 3% 的延遲改善，那在故障當下手動切 profile 這個動作就沒有意義，因為它本身就有風險，而且要有人在半夜醒著做。反過來，如果能換到兩倍，那就值得寫進 runbook。

沒有幅度，就沒有辦法決定要不要做。這是整個實驗的動機。

# §2 測試環境與判準

## 2.1 機器與 cluster

| 項目 | 規格 |
|---|---|
| Ceph 版本 | **v19.2.2** (squid)　※注意不是本 repo submodule 釘的 v19.2.3 |
| 位置 | Azure `japanwest`，共 15 台 VM、88 vCPU |
| OSD 機器 | 8 台 `Standard_L8s_v3`，每台 8 vCPU / 64 GiB RAM / 1.92 TB 本機 NVMe |
| OSD 數量 | **8 顆**（每台機器一顆，磁碟獨占） |
| 控制面 | 3 個 mon + 2 個 mgr |
| 壓力來源 | 4 台 fio client |
| 作業系統 | Ubuntu 22.04，kernel 6.8 系列（`linux-generic-hwe-22.04`） |
| pool 設定 | 副本數 3，`min_size` 2，PG 固定 128，autoscaler 關閉 |
| 故障域 | 8 顆 OSD 編成 **4 個合成機櫃**，每櫃 2 顆 |

兩個刻意的選擇要先講明白，因為它們限制了結論能推廣到哪裡。

kernel 特意選 `linux-generic-hwe-22.04` 而不是 Azure 專用的 `linux-azure`。因為使用者端的 I/O 走的是 krbd（在 kernel 裡的 RBD client），kernel 換掉，被測的程式碼路徑就換掉了。這裡要對齊的是正式環境，不是雲廠商的最佳化。

「機櫃」是合成的。所有機器掛在同一張網卡、同一個子網路下，所謂的機櫃隔離是用防火牆規則做出來的。這代表機櫃隔離的結果不能拿去推論真正跨可用區的網路故障。真實的跨區故障會有頻寬、延遲、封包遺失的差別，這裡完全沒有。

## 2.2 一個必須先講的邊界：三種 IOPS 不能直接比較

`osd_mclock_max_capacity_iops_ssd` 是 mClock 計算小 I/O 排程成本時使用的 **per-OSD 模型輸入**，不是 SSD 規格，也不是整顆 OSD 或整個 cluster 的硬性吞吐上限。Ceph 的編譯預設值是 21,500 IOPS；mClock 啟用且未略過開機測試時，OSD 會以一段 4 KiB random-write bench 取得同層級的替代值。

本次資料裡同時出現三種 IOPS。數字都是真的，但量的不是同一件事：

| 數字 | 統計範圍與 I/O 路徑 | 在本研究中的用途 |
|---|---|---|
| SSD raw fio：每顆 **276,735～304,158 IOPS** | fio 直接寫入單顆空白 NVMe；4 KiB random write、60 秒 | 檢查裸裝置上限與裝置間差異 |
| OSD 開機測試：每顆 **6,057～6,646 IOPS** | 單顆 OSD 經 ObjectStore／BlueStore；3,000 筆 4 KiB random overwrite，計時約 0.45～0.50 秒 | 提供 mClock 的 per-OSD capacity 模型輸入 |
| RBD fio：整個 cluster **63,634 IOPS** | 四台 client 經 RBD、網路、八顆 OSD 與三副本；4 KiB、讀寫 7:3、每輪 120 秒 | 校準完整 client 路徑的測試負載 |

這三種測試的受測物、讀寫比例、並行度、時間、副本工作與分母都不同。因此：

- 不能拿 raw fio 除以 OSD 開機測試，把差額全算成 BlueStore 成本。
- 不能把整個 cluster 的 RBD IOPS 除以八，稱為單顆 OSD 的真實能力。
- 不能因為 raw fio 最大，就把它直接寫進 `osd_mclock_max_capacity_iops_ssd`。

2026-08-07 在 Azure lab 以相同 OSD bench 參數重跑 5 顆 SSD OSD、每顆 2 次，10 筆主要樣本介於 5,831～6,264 IOPS，中位數 6,013 IOPS。這支持「約 6K 的 OSD bench 量級可重現」，但不會讓它變成 raw NVMe 或 RBD client 的量測。

campaign 使用 Ceph v19.2.2；上述 OSD bench 與 capacity 進入 scheduler 的路徑先以 v19.2.2 原始碼核對，再與 v19.2.3 做差異檢查，兩版在本報告依賴的量測契約與 capacity-to-cost 語意上沒有改變。獨立報告保留兩版的版本錨點與 line anchor。

campaign 開始前，我們把八顆 OSD 的 6,057～6,646 逐顆鎖住並關掉開機自動重測，讓十天下來三個 profile 都使用同一組 capacity input。這保住了 profile 間的條件一致性，卻沒有建立 capacity 高低的對照臂；因此本 campaign 不能回答「這組值是否唯一正確」或「換一組 capacity 是否會放大 profile 差距」。

三條 I/O 路徑、測試條件、原始碼依據與完整數字，見獨立報告 [〈mClock 的 SSD IOPS 為什麼不能直接跟 SSD raw fio 比〉](MCLOCK-IOPS-VS-RAW-FIO-COMPARABILITY-REPORT-2026-08-07.md)。

## 2.3 負載

兩種 I/O 形態，各自有四個壓力等級。

| 形態 | 參數 | 低 | 中 | 高 | 極限 |
|---|---|---|---|---|---|
| **4K 隨機讀寫**（讀寫 7:3） | 每台 client 4 個 job、佇列深度 16，共 16 job | 15,908 IOPS | 31,817 | 50,907 | 不限速（實測天花板 63,634） |
| **1 MiB 循序寫** | 每台 client 2 個 job、佇列深度 8，共 8 job | 594 MiB/s | 1,187 | 1,899 | 不限速（天花板 2,374） |

四台 client 各自有一顆 300 GiB 的 RBD image，亂數種子固定為 4242，所以不同 profile 之間打的是同一組 I/O 位址序列。每段測試跑 300 秒，前面加 30 秒暖機。

「極限」這一檔是閉迴路，不設速率上限，能跑多快跑多快。它跟其他三檔有本質差異，後面 §7 會說明為什麼這一檔的比值指標會騙人。

## 2.4 注入哪些故障

| 故障 | 做了什麼 | 想模擬的真實情況 |
|---|---|---|
| **單顆 OSD 下線** | 停掉一顆 OSD、等 OSD map 確認 down，再手動標記 out，觀察 backfill 到完成 | 一顆磁碟壞掉 |
| **機櫃隔離** | 用防火牆規則同時隔離合成機櫃的 2 個 node；兩邊 prepare／verify 都成功才標記兩顆 OSD out | 一個機架的交換器掛掉 |
| **整台 node 隔離** | 用防火牆隔離一個 node、等待 heartbeat 判定 down，再標記該顆 OSD out | 單機失聯 |
| **反覆上下線** | 同一顆 OSD 做 10 輪 stop／start；全程設 `noout`、不手動 out，每輪都等 down、up 與 PG active gate | 網路不穩或硬體間歇性故障 |
| **循序流量競爭** | 大 I/O 循序寫的同時觸發修復 | 備份視窗撞上故障 |
| **混沌注入** | seed 4242、1,800 秒；事件間隔 20～90 秒、單次維持 30～180 秒，實際產生 44 個 OSD／node／rack 事件 | 多重故障疊加 |

每次注入都受一個觀測上限保護：時間到了不管修復完成沒有都收工，避免一格卡死拖垮整個排程。單顆 OSD 下線、機櫃隔離、node 隔離的上限是 2700 秒，循序流量競爭是 3150 秒。這個上限後來變成一個大陷阱，見 §4.2。

## 2.5 量哪四件事

| 指標 | 定義 | 白話 |
|---|---|---|
| **修復完成時間**（秒） | 從注入動作開始，到所有 PG 回到 `active+clean` | cluster 花多久才把資料補齊 |
| **延遲惡化倍率** | 故障期間的 p99 延遲 ÷ 注入前 60 秒窗的 p99 延遲 | 使用者感覺慢了幾倍 |
| **最長停頓**（秒） | 所有 client 的每秒 IOPS 加總為零的最長連續區間 | 最久一次完全不動是多久 |
| **回填吞吐量**（MB/s） | 修復期間的資料複製速率 | 修復做得多快 |

> 一個命名上的教訓，先講在這裡。前兩份中期報告裡，「修復完成時間（秒）」和「回填吞吐量（MB/s）」在英文欄位名稱裡都叫 `recovery`。後來對帳時一度以為兩份文件的數字互相矛盾，追下去才發現是同名異物，兩邊各自算對，只是講的是不同的東西。這份報告一律用上表的中文全名，絕不共用「recovery」這個詞。

延遲惡化倍率的分母是「同一次執行裡、注入之前那 60 秒」，不是另外跑的基準測試。這是刻意的：用同一次執行的前段當分母，可以抵銷機器狀態隨時間漂移的影響。這個設計決定後來被證明是整個量測架構最正確的一件事，理由見 §8。

## 2.6 事前就講好的判定門檻

這些數字在開始跑之前就登記好了，過程中沒有調整過。

| 指標 | 要大於多少才算「有差別」|
|---|---|
| 最長停頓 | 差 2 秒以上 |
| 回填吞吐量 | 差 25% 以上 |
| 修復完成時間 | 差 300 秒或 20%，取大者 |
| 延遲惡化倍率 | 先算每次的 `r = 故障窗 p99 ÷ 同次執行的注入前窗 p99`；兩個 profile 以各自 replicate 的平均 `r` 比較，門檻為 `max(1.0, 兩組平均 r 的平均值 × 50%)` |

回填吞吐的 25% 與修復時間的 20%，分母都是兩個 profile 平均值的平均；差距等於門檻也算越過。若所有兩兩差距都小於門檻，就記為 `No hit`。noise margin 定義為同一測試格 replicate 的 pooled standard deviation 乘以 2；分析工具可優先使用故障資料，沒有才用穩態資料。本次凍結的 `margins.json` 沒有帶入故障資料，所以 p99 正式判定使用穩態資料算出的 0.065738。noise margin 大於或等於該組最大 production threshold 時標為 underpowered，較小才標為 equivalent。這裡的 equivalent 只是工具內部的工程門檻分類，不是有信賴區間的統計等價性檢定；它只細分 `No hit` 的原因，不會把 `No hit` 改成命中。完整的 profile 判定使用平均值；§5.1 的中位數與絕對毫秒只供人閱讀效果量。

另外兩條是事前設定、仍待目標環境驗證的營運政策門檻，跟 profile 比較無關：cluster stall 5 秒以上記警示，30 秒以上記嚴重。它們不是 VM block-layer timeout 的實測結果。

事前登記這件事本身很重要。如果門檻是看到資料之後才訂的，那「有沒有差別」就變成作文比賽。

## 2.7 可信度的防線

除了上面的門檻，還有四道機制在防止結果被污染：

- 每次切換 profile 之後，逐顆確認八顆 OSD 都真的生效，沒生效就不開跑。
- 跑對照組：完全不注入故障、只跑穩態負載，三個 profile 各三次。如果連沒故障的時候都量得出差別，那就代表量測本身有問題。
- 交錯排程：三個 profile 不是一個跑完再換下一個，而是輪替，避免時間趨勢被誤讀成 profile 差異。
- 覆蓋率打卡：一個獨立的監看程式定期記錄「量測工具還活著」，事後可以證明資料沒有缺口。

對照組的結果先講，因為它決定了後面所有數字的可信度。

穩態 4K 跑滿 36 次，三個 profile 的 IOPS 平均值最大只差 0.03% 到 0.48%，p99 延遲最大只差 0.011 到 0.699 毫秒。穩態循序完成 35 次，吞吐量最大差 0.30% 到 1.58%，p99 延遲最大差 0.841 到 2.447 毫秒。不過同一格重跑之間的落差最大到 8.913 毫秒，比組間差距還大。

**沒有故障的時候，沒有觀察到 profile-specific 的穩態偏差。** 這符合 mClock 份額只在資源競爭時咬合的預期，也排除了一個明顯的 profile-specific 混淆來源；它不能排除所有系統性偏差，故障結果仍須通過後續的有效性 gate 才能解讀。

| 循序流量競爭 | 循序 | 中/極限 | 6 | 12 | △ 中壓力可比（兩筆越過門檻但樣本不足）；不限速混用觀測上限，不可比 |

帳目要對得起來：177 次規劃 execution = 156 次完成 + 21 次未完成。那 21 次是混沌注入的 3 次（每個測試格需要一筆完成 execution，但各自重試三個 attempt 仍沒有 aggregate，見 §9），加上另外 18 次補樣本（分散在多個測試格，都是各自的第三或第四次，那些格子已有兩筆資料，補不補都不影響結論）。attempt 是 execution 內部重試，不另加進 177；沒有任何一格被悄悄丟掉。

上表的「可乾淨比較」是後面所有結論的基礎：三個 profile 都至少有兩筆資料，而且觀測上限相同。十二組故障測試中有八組符合，另外四組（三檔反覆上下線、加上循序不限速）混用了不同上限，依 §4.2 的理由不能合併比較。

「無法區分 profile」是本報告最重要的四個字，§5 展開。

## 3.1 開跑之前凍結的預測

計畫文件在各類實驗開始前留下了區塊層級的方向性預測，事後不得修改；但每一次執行的逐格預期欄位沒有填寫，不能稱為完整的逐格 preregistration。這些區塊級預測是從 mClock 的份額設計推出來的：如果 `high_client_ops` 給 client 的保底是 60%、`high_recovery_ops` 只給 30%，那故障期間前者的使用者延遲就該明顯比較低。

| 區塊 | 凍結的事前預測 | 推論依據 |
|---|---|---|
| 穩態對照（4K 與循序） | 三個 profile 應完全等效 | 沒有修復流量時，使用者流量是唯一活躍的類別，保底是下限而非上限 |
| 單顆 OSD 下線・低壓力 | 使用者面三者等效；**回填吞吐應 `high_recovery_ops` ≥ `balanced` ≈ `high_client_ops`** | 低壓力下 client 用不完資源，修復可以取用剩餘 |
| 單顆 OSD 下線・中壓力 | `high_recovery_ops` 的使用者延遲代價應明顯，另兩者相近 | 保底開始咬合 |
| 單顆 OSD 下線・不限速 | **延遲劣化應完整分離，`high_client_ops` 最輕、`high_recovery_ops` 最重，使用者吞吐約按 0.6 : 0.5 : 0.3 分配；修復時間則相反，`high_recovery_ops` 最快** | 資源完全飽和，保底份額應直接映射成吞吐比例 |
| 機櫃隔離・不限速 | **這應是全矩陣分離最大的區塊**；`high_client_ops` 保護使用者最好但修復最慢 | 兩顆 OSD 同時失效，修復量最大 |
| 反覆上下線 | 最長停頓三者等效（由 peering 主導）；**延遲分離應小於同壓力的單顆 OSD 下線** | 卡頓來自 peering 而非資源競爭，排程器插不上手 |
| 整台 node 隔離 | 對齊下線時間後應與單顆 OSD 下線中壓力無異 | 影響範圍相同，只是路徑不同 |
| 循序流量競爭 | 六格應全部等效 | 大 I/O 的成本模型若正確，profile 不該改變結果 |
| 混沌注入 | 累計停頓由少到多為 `high_client_ops`、`balanced`、`high_recovery_ops` | 同不限速的推理 |

上表這些預測底下還有一個共同的源頭，值得單獨拉出來，因為它是整個 campaign 唯一一個給了數字、而不只是給方向的預測；它也是後來確認有問題的地方。

開跑前的模型把整個 cluster 的 RBD 天花板 63,634 IOPS 除以八，再除以每顆 OSD 的 capacity input 6,439，得到係數 **1.235**。當時再用係數乘上壓力等級，估計使用者流量何時跨過各 profile 的 reservation：

| 壓力 | 佔天花板 | 換算後的需求比 | 事前預測 |
|---|---|---|---|
| 低 | 0.25 | 0.31 | 只有 `high_recovery_ops` 劣化，另兩者等效 |
| 中 | 0.50 | **0.62** | **三個 profile 完整分離，服務比例接近保底比例** |
| 高 | 0.80 | **0.99** | 同上；4K 故障矩陣未執行此檔，預測未檢驗 |
| 不限速 | 1.00 | **1.24** | 同上 |

同時凍結的還有它的推翻條件：**需求比 ≥ 0.6 卻量到三者無可執行的分離，就代表這個換算式漏了項。** 中壓與不限速兩個已執行檔符合推翻條件；高壓力未測，不列入證據。

收官後確認，這個係數把「整個 cluster、RBD 讀寫混合、三副本」的 IOPS，直接拿去除以「單顆 OSD、純寫 OSD bench」的模型輸入，分子與分母不是同一個量測契約（§2.2）。所以 1.235 只能保留為當時的事前預測與被推翻的模型，不能再拿來證明 capacity 偏低，也不能據此推算 reservation 已經緊繃。要回答後者，必須直接觀察每個 OSD shard 的 queue class 與 backlog。

一筆誠實的帳：這些預測寫在計畫文件層級，是「區塊」粒度而非「每一格」粒度，每次執行的紀錄檔裡，逐格的預期欄位是空的。這是這次實驗的一項證據債。下次應該在每一格開跑前把該格的預測數值也寫進紀錄檔，而不是只留在計畫裡。

# §4 讀結果之前：三個外表乾淨卻會騙人的資料陷阱

資料集的品質稽核結果是 156 筆已產生 `aggregate.json` 的完成資料列全部乾淨、零筆污染、零筆重複。它不包含在 attempt 階段就被拒絕、沒有產生統計檔案的嘗試；§9 會把這兩個分母對齊。這個數字很漂亮，但**乾淨不等於可用**。

以下三件事，自動化檢查全部沒抓到，每一筆的驗證狀態都是正常。如果你直接對結果目錄跑統計，就會踩到。這也是為什麼這一節排在結果之前，它是讀懂後面表格的前提，不是免責聲明。

## 4.1 一筆分母壞掉的資料，必須排除

延遲惡化倍率的算法是「故障期間 ÷ 注入之前」。分母壞掉，比值就沒有意義。

機櫃隔離、4K、低壓力、`balanced` 這一格的第二次執行，注入前那 60 秒的 p99 延遲量到 28.967 毫秒。同一批 4K 低壓力測試（32 次執行）的中位數是 2.376 毫秒，這一筆高了 12.2 倍。

結果是它的延遲惡化倍率被壓成 0.48，而同一格其他重跑是 5.66。看起來像是「故障期間反而變快」，實際上只是分母被灌水。

推測的成因是 fio 暖機期間的樣本落進了那 60 秒窗。發生率很低：它所屬的那組共 32 次執行只出了這一筆，而監看期間每兩小時掃一次、掃過 155 筆，也只抓到這一筆。

偵測方法很簡單，建議直接做進未來的流程：對每一組（形態 × 壓力）取出所有執行的注入前窗 p99，偏離該組中位數 50% 以上的就當離群，人工複查。

這一筆已從本報告所有統計中排除。

## 4.2 觀測上限決定了被截斷格子的數字

「反覆上下線」這個故障從來沒有自己解除過，OSD 一直在掉線又回來，PG 永遠回不到全乾淨。所以每一次都是撞到觀測上限才收工。

問題在於，這批測試的上限不一致。救援重跑的時候把上限從 2700 秒放寬到 5400 秒，於是：

| 觀測上限 | 筆數 | 延遲惡化倍率 | 中位數 |
|---|---|---|---|
| 2700 秒 | 6 | 3.09 / 3.71 / 4.56 / 4.63 / 4.80 / 4.99 | 4.60 |
| 5400 秒 | 2 | 11.98 / 12.13 | 12.06 |

看起來差了 2.6 倍，但兩種觀測上限與不同 profile 混在一起，無法把差距歸因於 profile 或觀測時間。

機制很直白：累計型的指標（例如總劣化秒數）幾乎正比於觀測上限，實測「總劣化秒數 ÷ 上限」穩定落在 0.78 到 0.86 之間。故障既然不會自己好，你量多久就壞多久——這種指標量的是「你看了多久」，不是「cluster 有多糟」。

所以跨上限的數字絕對不能合併平均。先前若用整個反覆上下線組比較 profile，觀測上限就是混雜因素，不能據此建立 profile 排名。

最長停頓在本資料裡沒有觀察到明顯的觀測窗效果：上限 2700 秒時量到 21～28 秒，上限 5400 秒時量到 22～24 秒，兩者重疊。這只支持把它列為下一輪較不受累計時間影響的候選指標，不足以稱為與上限無關。

## 4.3 「機櫃隔離注入時間差過大」的證據不足

這項注入時間檢查總共送出 14 次警示。它們是 validity flag，不是 §15 audit 裡的完成資料列污染計數；現有報告只找到其中四筆同時保留 wrapper 差距與 OSD map epoch，可做下表對照。

自動化檢查認為：隔離一個機櫃的兩顆 OSD，動作之間如果差超過 5 秒，就不算「同時失效」，資料要作廢。下表四筆的 wrapper 差距都是 7 秒，因此觸發警示；其餘十次沒有足夠欄位可在本報告重建精確差距。

追下去發現檢查量錯範圍。程式從第一台機器準備防火牆規則之前算到第二台機器掛上規則之後，中間涵蓋了四次 SSH 往返；但真正造成隔離的只有中間那兩次。四筆完整紀錄的 wrapper 都量到 7 秒，與多次 SSH 往返耗時相容，但沒有逐次 SSH timestamp，不能再拆成固定的單趟時間。

Ceph 的 OSD map 紀錄顯示兩顆 OSD 的下線事件只差 1～2 個 epoch，與接近同時失效相容；但 epoch 是版本序號，不是 elapsed time，現有資料沒有 timestamp 可以把它換算成秒：

| 注入時間 | wrapper 算出的差距 | 第一顆 OSD 下線 epoch | 第二顆 | map epoch 差 |
|---|---|---|---|---|
| 07-28 07:28 | 7 秒 | 966 | 968 | 2 |
| 07-28 07:59 | 7 秒 | 1364 | 1366 | 2 |
| 08-01 03:58 | 7 秒 | 11806 | 11808 | 2 |
| 08-01 05:30 | 7 秒 | 12185 | 12186 | 1 |

因此，wrapper 的 7 秒不能直接當作兩顆 OSD 真正失效的時間差，map epoch 差也不能反過來證明差距小於 5 秒。本報告保留這批結果，但把精確注入時間列為未解的量測缺口；下次必須在兩次生效動作旁直接記單調時鐘 timestamp。

這個缺陷沒有修，是刻意的決定：它不會阻擋測試完成，而在 campaign 進行到一半去改注入路徑，風險高於收益。記錄在案比手癢去改更安全。

# §5 主結果：可以比較的八組，沒有形成可執行的 profile 排名

先把可比較的範圍講清楚。十二組故障測試裡三個 profile 都有至少兩筆資料，但其中四組（三個反覆上下線、加上循序不限速）混用了不同的觀測上限，依照 §4.2 自己訂下的規則，這四組不能合併比較。剩下八組觀測條件完全一致，是本節的分析對象。

## 5.5 為什麼分不出來：三個比「cluster 太小」更近的候選解釋

分不出來是量測事實。但「為什麼分不出來」是另一個問題，而最容易脫口而出的答案是：cluster 太小，mClock 還沒被逼到會咬合的位置。

那個答案可能對，但目前還有三個更近的候選機制，可能在 mClock 發揮之前先限制了可見差異。三者都不必先換更大的 cluster 就能驗證，而且都與本次設定或觀測缺口有關。

**第一，部分副本工作繞過一般 mClock class。**

一個使用者的寫入進到 Ceph，會變成三個動作：主副本 OSD 自己寫一份，再轉發兩份給另外兩顆 OSD。mClock 只把第一種算進「使用者流量」這一類。後面那兩份轉發過來的請求，在原始碼裡走的是一條叫 `immediate` 的特快通道，直接跳過整個排程器。

這條路徑差異是機制層級的事實，但本 campaign 沒有收每個 queue class 的組成，所以無法從 aggregate RBD IOPS 算出「有幾成工作繞過排程器」。舊版報告曾用 cluster IOPS 拆算出 37.5%；該數字依 §2.2 的比較邊界撤回。

**第二，實驗沒有證明各 OSD shard 上真的存在兩類持續 backlog。**

capacity input 越小，mClock 對小 I/O 記的最低成本越高，換算出的 reservation IOPS 也越低；但這不等於整顆 OSD 被硬性限速。對 client 與 `background_recovery`，本次三個內建 profile 的 limit 都是無上限，reservation 用完後仍會進入 weight 競爭。

因此 capacity 與 profile 差距不是「設得越高或越低，差距必然越大」的單調關係。只有 client 與正確的 recovery class 在同一個 OSD shard 持續排隊，送入的負載又超過當下可服務量時，reservation 與 weight 的差異才有機會清楚出現。本 campaign 沒有收 per-shard queue backlog，也只使用一組 6,057～6,646 的 capacity input，不能判定這組值抹掉或放大了 profile 差異。

**第三，修復的併發度被另一個參數卡死。**

Ceph 在 mClock 模式下會強制把「同時進行的 backfill 數量」設成 1。這是排程器之外的另一道閘門：修復流量還沒排到 mClock 面前，就先被這道閘門掐住了。

份額只有在「兩邊都想要更多」的時候才有意義。如果修復這一邊根本產不出足夠的請求來競爭，那 40% 和 70% 的保底就沒有差別——不是排程器不管用，是它沒有東西可管。

這一條在開跑前的假說文件裡就寫好了處置方式：三個 profile 若無法區分，報告必須註明「上限參數在這個拓撲下不可觀測」。這裡補上。

**三條合起來**的意思是：「換一套更大的 cluster 就分得出來了嗎」可能問錯了方向。更該先問的是「實際工作進了哪個 queue class、每個 shard 是否同時 backlog、修復工作是否在排程器前就被併發度限制」。本 campaign 沒有收齊這三項直接證據，所以它們是下一輪要裁決的候選機制，不是已被證明的根因。

沒有一條推翻 §5 的結果。它們改變的是這個結果該怎麼讀，而那正是下一節的事。

## 5.6 結論怎麼寫才誠實

在這個 cluster 規模、這個配置與這個樣本數下，**修復完成時間、延遲惡化倍率、最長停頓這三個指標都不具備區分 profile 的能力。**

這句話的重點是：八組比較沒有形成跨指標一致、越過事前門檻且樣本足夠的結果。部分排序已被後續樣本改變，其餘多數只有兩到三筆；硬湊一個 profile 排名，會把樣本不足的描述性差距誤寫成決策證據。

但同樣不能寫成「mClock profile 沒有用」。加上 §5.5 之後，最誠實的一句是：**本實驗沒有證明形成了足以讓三個 profile 分流的競爭條件；在現有配置、觀測與樣本數下，八組比較都沒有看到 profile 分開。** 這支持「目前沒有證據值得在故障時切換」的保守決策，不支持「profile 永遠沒有差別」。

# §6 值得下一輪驗證的次要結果：不限速時的吞吐達成率

有一個指標在一個特定情境下表現得完全不同。

吞吐達成率指的是故障處理完之後，重新量到的 4K 吞吐相對於校準天花板（63,634 IOPS）的比例。在「單顆 OSD 下線 + 4K + 不限速」這一格：

| profile | n | 各次的值 | 平均 | 組內全距 |
|---|---|---|---|---|
| `high_client_ops` | 3 | 1.0247 / 1.0250 / **1.0009** | 1.017 | 0.0241 |
| `balanced` | 2 | 0.9042 / 0.9064 | 0.905 | 0.0023 |
| `high_recovery_ops` | 2 | 0.8822 / 0.8840 | 0.883 | 0.0018 |

**三組的數值範圍完全不重疊**——`high_client_ops` 最低的 1.0009 仍高於 `balanced` 最高的 0.9064，`balanced` 最低的 0.9042 仍高於 `high_recovery_ops` 最高的 0.8840。組間差距是組內波動的 4.6 到 9.7 倍。

> 這個比值的算法是「兩組平均值之差 ÷ 兩組之中較大的那個組內全距」。三組兩兩相比分別得到 4.64（`high_client_ops` 對 `balanced`）、5.56（`high_client_ops` 對 `high_recovery_ops`）、9.70（`balanced` 對 `high_recovery_ops`）。上表的全距是用未四捨五入的原始值算的，所以拿表上四位小數自己減會有末位差異。

本次觀測的排序符合 mClock 的設計意圖：偏袒使用者流量的 profile 量到最高吞吐，偏袒修復的 profile 最低，預設值在中間。它值得下一輪用事前門檻與更多樣本驗證，但現階段不能稱為已確認的 profile 效果。

## 6.1 為什麼它還是不能拿去上線

四個理由，每一個單獨都足夠：

1. 它不是事前登記的主要指標。沒有預先設定的門檻、沒有事前的檢定計畫。事後才挑出來的指標，天生就有挑選偏誤。
2. 樣本仍然太少（兩到三筆）。
3. 同一個指標在機櫃隔離情境下不成立。那一組 `high_client_ops` 自己組內就差 0.244，比三組之間最大的 0.187 還大。**只有單顆 OSD 下線這一組能保留。**
4. 它量的是「事後」不是「當下」。這是故障處理完之後重測的吞吐，不是使用者在故障當下的體感。

## 6.2 第三筆樣本如何改變結果幅度

這個結果最初被記錄下來的時候只有兩筆：1.0247 和 1.0250，組內全距只有 0.0003，組間是組內的 10 到 70 倍；兩筆樣本讓效果幅度看起來特別大。

收官對帳時，我們在資料裡找到一筆兩份中期報告都沒有納入的第三次執行。它狀態完全乾淨——正常完成、未被污染、未被截斷、觀測上限相同——只是漏算了。它的值是 1.0009。

加進去之後，組內全距從 0.0003 變成 0.0241，放大了 80 倍；組間對組內的比值從「10 到 70 倍」掉到「4.6 到 9.7 倍」。

**加入第三筆後，本次仍觀測到相同排序，但幅度比兩筆樣本時小。** 這再次說明小樣本排序不穩定；它值得下一輪驗證，不適合作為立即切換 profile 的依據。

這就是為什麼這份報告不用兩個樣本下任何結論。

# §7 為什麼不能跨壓力比較

延遲惡化倍率有一個很容易誤用的性質：它是比值，而分母隨壓力等級劇烈變化。

同樣是機櫃隔離，倍率在不同壓力下是這樣的：

| 壓力 | 延遲惡化倍率 | 注入前的 p99（分母） |
|---|---|---|
| 4K 低壓力 | 5.7 ～ 6.2 | 約 2.4 毫秒 |
| 4K 中壓力 | 5.6 ～ 8.2 | — |
| 4K 不限速 | **1.4** | 約 52 毫秒 |

不限速那一檔看起來「幾乎沒受影響」，但那是假象：分母本來就已經很大了。系統在不限速時本來就跑在延遲的懸崖邊，故障造成的絕對衝擊被巨大的分母壓平。循序不限速的分母更誇張，約 105 毫秒。

反方向也一樣極端：反覆上下線在 4K 低壓力下，分母只有 2.4 毫秒，倍率直接爆到 313 到 476。

**同一個故障，在不同壓力下的比值差兩個數量級。**

所以：不限速與循序這兩個區間，應該改看絕對值（最長停頓秒數、總劣化秒數），而不是倍率。跨壓力等級直接比倍率，會得出完全相反的結論。

# 第二部：這種實驗要怎麼做才不會白做

這一部跟 mClock 無關。它記錄的是量測架構本身的失敗，對下一個要做故障注入實驗的人（包括未來的我們自己）比 profile 結論更有用。

# §8 有效性檢查：七次假警報、六種失敗模式

我們設了一道自動檢查，用來偵測「機器狀態隨時間漂移」：如果今天的基準比歷史同條件的中位數差太多，就停下佇列等人來看。

**八天之內它擋下佇列七次。七次全部是假警報，一次真陽性都沒有。**

七次事件呈現六種失敗模式；前兩次是同一種條件不一致問題重複發生：

| 警報事件 | 到底哪裡錯了 |
|---|---|
| 1、2 | 同一種失敗模式：校準時沒有取樣程式在跑，拿來當基準的資料與實測條件不同 |
| 3 | 新組合才跑三次就開始判漂移，樣本根本不夠 |
| 4 | 參考池把不同故障型態混在一起比，等於拿蘋果比橘子 |
| 5 | 全體共用一個門檻，但每種組合本來的正常離散度天差地遠，粗門檻抓不到細異常 |
| 6 | 算「連續超標幾次」的時候又回頭用全體共用的計數，沒有照組合分開算 |
| 7 | 一個本來只看絕對值的檢查，被拿去累計「連續漂移」，語意根本對不上 |

六種失敗模式的骨子裡是同一件事：**判準的某個維度，沒有跟著資料的實際結構走。**

門檻數值從頭到尾沒有調過一次。容忍度 0.15、離散度乘數 3.0、達成率下限 0.85、連續次數 3，全部是原始值。修正處理的是「同條件」怎麼定義，不是數字大小。

## 8.1 最根本的一條：它量錯了東西

這道檢查用的是故障處理完之後的重測值。而那個值本身就極度不穩定：修復尾段的離散度高達 29.2%，最大最小值差 8.5 倍。拿一把會自己抖動 8 倍的尺去量漂移，當然一直誤報。

而更好的儀器就在旁邊。每一次執行注入之前那 60 秒窗，跨八天、在八個不同組合上，離散度只有 1.1% 到 9.5%。

同一份資料裡就躺著一把穩定得多的尺，只是沒被拿來用。

## 8.2 可以帶走的通則

> 以「歷史同條件中位數」為基準的漂移檢查，**失敗模式集中在「同條件」的定義，不在門檻數值。**
>
> 設計的時候應該先窮舉所有會讓量測條件系統性偏移的變因，再決定要分幾層；而不是先訂一個門檻，等它報警了再回頭補分層。

最終的處置是：漂移檢查改為只告警、不停佇列。判定邏輯與所有資料有效性檢查一律不動，訊號照常記錄下來供事後稽核。降低誤報的成本，但不減少證據。

# §9 混沌注入在這套量測架構下不可驗證

三個混沌測試格，零筆數值資料。原因不是 cluster 撐不住，是量測工具自己被打掛了。

覆蓋率打卡的統計說明了一切：

| | 混沌注入 | 一般故障型態 |
|---|---|---|
| 涵蓋秒數 | 約 1826 | 約 1800 |
| 缺口 / 缺口秒數 | 0 / 0 | 0 / 0 |
| 無法佐證的秒數 | **547 / 592 / 608（約 33%）** | 9 ～ 10 |

差了 55 到 68 倍。

成因很直接。混沌注入在 30 分鐘內打了 44 個事件，反覆隔離多台機器；而覆蓋率監看程式是靠 SSH 進去打卡的，於是它的打卡路徑正好被自己注入的故障切斷，每次斷 60 到 90 秒。

三個測試格各重試三次，九次都在產生統計結果前因涵蓋證據不足而被拒絕。稽核按「每個測試格至少要有一筆完成結果」計數，因此帳面是 **3 筆缺件、3 格待人工處理**（`needs-human`），不是 9 筆完成資料。污染 0 的分母只包含已產生 `aggregate.json` 的 156 筆完成資料列，不包含這九次失敗重試。逐秒串流雖記為沒有缺口（`gaps=0`），約三分之一秒數仍缺少獨立監看證據，所以不能宣稱涵蓋完整。

這是「被測系統的故障會反過來干擾量測工具」的極端版本，指向一個很明確的改進方向：覆蓋率打卡不該依賴會被故障影響的路徑。

另外還有一個尚未修的程式缺陷：混沌注入寫入的時間戳欄位名稱與統計程式讀取的不一致，會導致統計走錯分支。在任何混沌測試重跑之前，這兩件事都必須先修。

# §10 監看程式分不出「死了」和「刻意停手」

佇列有一個監看程式，負責在佇列意外死掉時把它拉起來。舊版只用「行程還在不在」來判斷。

問題是，佇列被 §8 那道檢查刻意停下的時候，行程也不在。於是監看程式反覆把它拉起，佇列一起來就再度自我停止；日誌在 43 分鐘內記了 40 次重啟，直到撞上重啟次數上限才罷手。舊報告曾概括成「每兩分鐘一次」，但這與日誌總次數及經過時間對不上，因此撤回固定頻率的說法。

修正後在真實環境驗證通過：偵測到「刻意停手」狀態就留言收工，重啟次數 0。

順帶抓到一個更難查的方向：舊版比對行程名稱的方式，會誤匹配到靜態檢查工具正在檢查那個腳本的行程。而靜態檢查每次測試前都會跑——也就是說，**佇列真的死掉的時候，監看程式反而可能一路睡下去。** 這是比誤判「刻意停手」更危險的失敗模式。

# §11 為什麼 campaign 不會靠變異下降提早收斂

排程器有一個自動補樣本的機制：某個測試格的變異係數超標，就要求多跑幾次，上限五次。設計意圖是「不夠穩就多量幾次」。

但這些格子補樣本後，變異並沒有下降。於是提早收斂的條件失效：變異大 → 要求補樣本 → 補完變異還是大 → 繼續要求，直到每格五次的硬上限。現有資料沒有識別變異的成因，不能進一步稱它是物理限制。

實測的樣子是這樣：待辦數量連續七次檢查都停在 17。八小時內完成了 5 次執行，同時新增了 5 次補樣本要求，淨進度為零。

這本身就是一條方法論教訓：

> **以變異係數為觸發條件的自動補樣本機制，遇到補樣本後變異仍未下降的量，會一路補到每格硬上限，短期內可能出現淨進度為零。**
>
> 現有的每格五次上限能阻止無界重跑；若要提早結束，還需要在偵測到「補了樣本變異沒下降」時改為回報而非續補。

這也是為什麼 campaign 在此停手是一個決定，而不是等待變異自然下降；否則它會把這些格子一路補到每格硬上限才結束。

## 11.1 環境雜訊（順帶說明部分污染標記）

中斷前的日誌出現過 SSH 連線逾時與網路不可達。網路瞬斷造成覆蓋率監看程式少打一次卡（25 秒），於是那次執行被判定證據不足。

檢查的判斷是正確的（證據確實缺了一段），但成因是無害的雲端網路抖動，不是量測缺陷。記在這裡，避免未來把這類標記誤讀成資料有問題。

# §12 建議總表

證據等級分三種：**實測**＝這次實驗直接量出來的結論；**實證事實**＝過程中確認、但不是本實驗的待答問題；**推論**＝根據觀測值做的合理外推，尚未直接驗證。

| # | 對象 | 建議 | 證據等級 | 依據 | 可改動性 |
|---|---|---|---|---|---|
| 1 | mClock profile | 維持預設 `balanced`，現階段不為故障情境切換 | 基於實測的保守決策 | §5 | 執行中可改，但現有證據不支持切換 |
| 2 | OSD 容量參數 | 逐顆確認生效值與來源；不要以 raw NVMe 或 cluster RBD IOPS 直接覆寫 | 實證事實 | §2.2、§5.5 | 執行中可改；改前須做配對測試 |

| 4 | VM 內的磁碟逾時 | 先量 VM block layer 的 command timeout；60 秒只作待驗證候選值 | 推論（未驗證） | §5.4 | 驗證前不改正式環境 |

## 12.1 前四條該怎麼執行

**第 1 條，維持預設。** 八組比較沒有形成跨指標一致且越過事前門檻的 profile 排名，修復完成時間更是一次都沒有越過門檻。這是「現有證據不支持切換」的保守決策，不是三個 profile 等價的證明。適用條件是八顆 OSD、本機 NVMe、每格兩到三個樣本；換一個規模要重測。

**第 2 條，容量參數。** 先逐顆回讀，確認目前值、來源與開機測試是否啟用。本次 6,057～6,646 IOPS 是 per-OSD OSD bench，八顆的變異係數 3.19%；相同 bench 在 2026-08-07 重跑的 10 筆主要樣本中位數是 6,013 IOPS，量級可重現。在沒有同層級的持續型 OSD 校準與配對測試前，保留這組經一致性檢查的值，比拿 raw fio 或 cluster RBD IOPS 覆寫安全。

以下命令只適用於「已經決定要凍結候選值做配對實驗」的情境，不是本報告對正式環境下達的通用處方：

```bash
# 對每一顆 OSD 各做一次，<value> 換成該顆的值
ceph config set osd.<id> osd_mclock_max_capacity_iops_ssd <value>
ceph config set osd.<id> osd_mclock_skip_benchmark true

# 設完回讀確認，這兩個值都必須跟你設的一致
ceph config show osd.<id> | grep -E 'max_capacity_iops_ssd|skip_benchmark'
```

值從哪裡來，證據邊界是：raw fio 只能比較裸裝置，OSD bench 最接近 per-OSD capacity input，RBD fio 則是完整 cluster 的 client 結果。三者不能互換，也不能把 cluster IOPS 除以 OSD 數量後稱為單顆能力。若要人工覆寫，下一輪必須固定 profile、負載與故障，只改 capacity 候選值，並同步確認 per-shard queue class 與 backlog（§2.2、§5.5）。

**第 3 條，別讓 OSD 反覆上下線。** 同壓力比較，低壓力 p99 是 8.5～9.6 對 734～1,585 毫秒，中壓力是 10.7～13.0 對 304～472 毫秒，不限速是 55.3～60.6 對 156～271 毫秒。單顆 OSD 乾脆下線約十二分鐘修復；反覆上下線在觀測期間未完成。

先查現有 unit 的設定與實際計數方式。cephadm 產生的 OSD systemd unit 可能帶有 `StartLimitInterval` 與 `StartLimitBurst`；若目標 unit 有設定，達到門檻後會進入 `failed (Result: start-limit-hit)`。版本、unit override 與「啟動次數／重啟次數」的計數語意都會影響第幾次被擋，不能把它寫死成「30 分鐘內第五次」。請在目標 node 執行：

```bash
systemctl show ceph-<fsid>@osd.<id>.service \
  -p StartLimitIntervalUSec -p StartLimitBurst -p Result -p NRestarts
```

若查到目標 unit 確實設定了重啟保護，再針對 `start-limit-hit` 獨立設告警，不要只看 Ceph health；OSD 被 systemd 放棄後，Ceph 的健康摘要不一定會指出停止重啟的原因。同時檢查 `mon_osd_down_out_interval`，避免故障 OSD 長時間停在 down 但未 out。

> 本實驗的反覆上下線是受控執行 10 輪 OSD service stop/start，並全程設定 `noout`；它不是 daemon 自發 crash 後由 systemd `Restart=` 反覆拉起的 crash loop。campaign 沒有收集目標 unit 的 `StartLimit*`、`Result` 或 `NRestarts`，因此不能用這組實驗判定何時會觸發 `start-limit-hit`。

**第 4 條，VM 內的磁碟逾時。** 本 campaign 的「最長停頓」是所有 client 每秒 IOPS 合計為零的連續區間，不是 VM 內單一 SCSI command 的 elapsed time；兩者不能直接互換。我們沒有在 VM block layer 觀測 command age、timeout 或 retry，因此 **目前不要僅憑 20～28 秒 cluster 停頓就把 timeout 改成 60 秒**。60 秒只能列為下一輪候選值：先在 VM 內同步收 block-layer trace 與 I/O error，再用可回退的故障測試確認 30 秒是否真的撞線。使用 virtio-blk 的 VM 也沒有 SCSI device timeout 這個設定，需要另驗應用層重試。

## 12.2 最該帶走的不是答案，是副產品

這是整份報告最反直覺的地方。我們花 230 小時想知道「該切哪個 profile」，現有答案是：**八組比較都沒有提供足以支持故障時切換的證據。**

但同一批資料指出了三件更值得帶走的東西，而且一件比一件不像答案。

**能立刻照做的是避免 OSD 反覆上下線，並先查現有重啟保護。** 低壓力的同壓力比較是 77～187 倍，中壓力是 23～44 倍，不限速時則縮為 2.6～4.9 倍；反覆上下線在觀測期間都未完成修復。這個故障型態的效果遠大於 profile 間差距，但 systemd 的門檻是否存在、何時觸發，仍要在目標 unit 查證。

**第二條是一個沒答完的題目。** 本次只證明三個 profile 使用同一組 per-OSD capacity input，沒有證明 6K、21.5K 或 raw fio 的數字哪一個是正式環境的正確設定。三種 IOPS 不能互比；capacity 該設多少，必須用同層級的候選值做配對測試。這是下一輪實驗的第一個題目，不是立刻照做的處方。

**第三條根本不是建議，是一個提醒。** 我們花了 230 小時去比三個 profile，卻沒有同步證明工作實際進了哪個 queue class、每個 shard 是否有兩類持續 backlog，以及 recovery 是否先被併發度卡住（§5.5）。任何想重做的人，應該先把這三個觀測 gate 補齊，再開機器。

# §13 限制：哪些綁這個環境，哪些是機制層級

限制分兩種，要分開看：一種是「換個環境結論就不成立」，一種是「這次的配置讓實驗本身沒問到該問的問題」。第二種比第一種嚴重，先講。

**配置與觀測層面的限制（§5.5 展開）。** 部分副本工作會走高優先度路徑，修復併發度另有閘門；但本次沒有收 per-shard queue class 與 backlog，無法量出各路徑比例，也無法證明 reservation 是否真的咬合。換一套更大的 cluster 不會自動補上這些證據，重做前要先補觀測 gate。

**環境層面的限制。** cluster 小：八顆 OSD、每台一顆，修復一顆只需要在剩下七顆之間搬資料；在幾百顆 OSD 的 cluster 上，份額很可能在完全不同的位置咬合。而且樣本數普遍只有兩到三筆。機櫃是合成的：同一張網卡、同一個子網路，用防火牆規則做出來，不能拿來推論真正的跨可用區網路故障——真實跨區故障有頻寬、延遲、封包遺失，這裡一項都沒有。磁碟是本機 NVMe：換成 SATA SSD 或機械硬碟，資源競爭的形態會完全改變。

**可以帶走的機制級結論有限但明確。** capacity 是 mClock 的排程模型輸入，不是硬性 IOPS 上限；不同量測層級的 IOPS 不能互換（§2.2）。「該設多少」這次沒答出來。累計型指標會被觀測窗長度污染（§4.2）、比值型指標在分母大的區間會失去解析度（§7），這兩條是量測學，跟 Ceph 無關。第二部那四條方法論教訓（§8～§11）講的是實驗架構本身的失敗模式，換個系統照樣成立。

最後一件必須說清楚的事。**本報告沒有證明三個 profile 相等**，它證明的是「在這個規模、這個配置、這個樣本數下，用這三個指標區分不出來」。我們沒有做等價性檢定，也沒有給信賴區間。這兩句話不一樣，不要簡化成前者。

# §14 未解問題與下一步

1. **容量參數該設多少？**（§2.2、§5.5）現有三種 IOPS 不是同一層級，不能先替它們排出「偏低、正確、偏高」。要答就得選定同層級的 per-OSD 候選值，固定故障、負載與 profile 做配對測試，並先確認 queue class 與 backlog。這一題不先答，重跑故障矩陣仍無法識別 capacity 的因果效果。
2. **有多少工作繞過一般 mClock class？**（§5.5 第一點）需要在故障期間收每顆 OSD 各類佇列的長度組成，直接驗證高優先度路徑佔比。這次的資料收集沒有涵蓋，不能沿用舊版的 37.5% 拆算。
3. 吞吐達成率的排序值不值得追？（§6）本次在單顆 OSD 下線、不限速的測試格觀測到符合設計意圖且值域未重疊的排序。要確認需要：把樣本補到五筆以上、事前登記門檻，並確認它在單顆 OSD 下線以外的情境是否成立。capacity 改變後排序會變強或變弱，應列為配對測試的待答問題，不先假定方向。
4. 混沌注入必須換一套打卡機制才能測。（§9）覆蓋率證明不能走會被故障切斷的路徑；時間戳欄位名稱不一致的缺陷也要先修。
5. 更大的 cluster 會不會就分得出來了？八顆 OSD 可能根本沒把 mClock 逼到會咬合的位置。這題排在後面而不是最前面，是因為 §5.5 那三個候選原因不需要換規模就存在——先取得它們的直接證據，這一題才問得乾淨。
6. 機櫃隔離的注入時間差量測範圍（§4.3）仍是錯的，只是被記錄下來而非修正。下次重構注入路徑時應一併修好。
7. 成本從未與 Azure 實際帳單對帳。（§15）

# §15 資料集最終狀態與成本

稽核產生時間 2026-08-06 03:15 UTC：

```
完成 156 / 規劃 177　測試格 63　缺件 21
重複 0　被截斷 24　污染 0　待人工 7　放棄 0
```

這幾個數字分兩組讀。「完成／缺件」是互斥的帳，156 + 21 = 177 剛好是規劃總數；「被截斷／污染／待人工」則是標籤，會跟前面那組重疊，不要拿去相加。

- 63 個測試格全部有資料，混沌注入的 3 格除外。
- 污染 0、重複 0 的分母是 156 筆已產生 `aggregate.json` 的完成資料列。混沌注入的 9 個失敗 attempt 在 aggregate 產生前就被拒絕，因此反映在 3 筆缺件與 3 格待人工，不會出現在這個污染計數。
- 被截斷 24 筆全部出自反覆上下線，屬預期行為（§4.2）。這 24 筆算在「完成」裡，資料可用，只是修復時間要當成下限讀。
- 待人工 7 筆 = 混沌注入的 3 格 + 先前累積的 4 筆。那 4 筆是循序高壓對照組一筆、反覆上下線三筆，全都因為 execution 內連續三個 attempt 被 validity check 拒絕或中斷而自動跳過；它們沒有進入 156 筆完成資料列的污染分母。
- 缺件 21 筆 = 混沌注入 3 次 + 另外 18 次執行（分散在多個測試格，是各自的第三或第四次補樣本）。混沌那 3 次同時也掛著待人工的標籤，是同一件事的兩個面向，不是兩筆帳。那些測試格都已經有兩筆資料，補不補都不影響結論。
- 「放棄」為 0，意思是沒有任何一格被正式除名。混沌注入雖然拿不到資料，帳面上仍保留為待處理，沒有從矩陣裡刪掉。

cluster 收工時的狀態是乾淨的：129 個 PG 全部 `active+clean`，8 顆 OSD 全部 up 且 in，沒有殘留的隔離規則。健康狀態顯示兩則警告，來自實驗刻意設定的停用 scrub 旗標及其衍生警告，不是損壞。

**成本：約 229.4 小時、估算約 US$1,840。**

> 這是估算，不是帳單。算法是「從 campaign 起算到現在的實際經過時間 × 固定機隊費率 US$8/hr」，假設整段期間機隊規模不變、且不扣除任何閒置。**實際 Azure 帳單從未取得，也未對帳。** 早期日誌裡的 170.67 小時 / US$1,365 與 179.9 小時 / US$1,439，是同一個公式在較早時間點的取樣，不是另外兩種估法。
