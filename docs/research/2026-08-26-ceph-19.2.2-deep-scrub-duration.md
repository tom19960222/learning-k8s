# Ceph 19.2.2：2048／4096 PG 的自動 deep scrub 週期與容量估算

日期：2026-08-26
研究版本：Ceph `v19.2.2`，tag commit `0eceb0defba60152a8182f7bd87d164b639885b8`

## 結論

只給 PG 數，**算不出實際 deep scrub 執行時間**。PG 可以是空的，也可以裝數 TiB 資料；deep scrub 會讀取 object 內容並比對 primary 與 replica，所以時間還取決於資料量、object／omap 數量、pool `size` 或 EC profile、OSD 數量與媒體、client 負載、recovery，以及 scrub backlog。

如果問題是「維持 Ceph 19.2.2 預設值時，系統多久應讓每個 PG 至少完成一次 deep scrub」，可以先用下列結論規劃：

- `2048 PG`：正常且容量足夠時，視為約 **7 天一輪**；要在 7 天預算內完成，cluster 平均至少要完成 **292.6 PG/day、12.2 PG/hour，約每 4 分 55 秒完成 1 個 PG**。
- `4096 PG`：正常且容量足夠時，同樣約 **7 天一輪**；但需要 **585.1 PG/day、24.4 PG/hour，約每 2 分 28 秒完成 1 個 PG**，PG scheduling／協調率是 2048 PG 的兩倍。若兩種設定承載的 logical bytes 相同，主要 scan bytes 不會因此變成兩倍，只是每個 PG 較小、固定 overhead 較多。
- 若所有 PG 的 `last_deep_scrub_stamp` 在同一刻起算，19.2.2 的自動 scheduling 不是剛好在第 7 天同時跑完。在忽略 tick backoff、queue delay、實際 I/O 時間、recovery 與 PG 不乾淨的 toy model 裡，最後一批會在 **7～8.5 天內取得 deep scrub 候選機會**；這不是完成時間保證。
- 即使其他條件都正常，66% tick backoff 本身也有無界的幾何尾端，再加上 queue、recovery、not-clean PG、`nodeep-scrub` 與實際 I/O，原始碼不存在有限的完成時間上界。
- 真實 cluster 若無法長期維持上述完成率，4096 PG 會比 2048 PG 更容易出現 `PG_NOT_DEEP_SCRUBBED`，不能靠「預設是 7 天」推論一定跑得完。

自動 periodic scrub 是每個 PG 各自滾動 scheduling，並不存在 pool 層級一次啟動、一次收工的固定 batch。因此「一輪」應定義成：在選定觀察起點後，pool 內每一個 PG 都至少出現一次新的 `last_deep_scrub_stamp`。

## 原始碼中的 scheduling 流程

### 1. 19.2.2 的預設 deep scrub interval 是 7 天

[`src/common/options/osd.yaml.in`](https://github.com/ceph/ceph/blob/v19.2.2/src/common/options/osd.yaml.in#L453-L468) 定義：

- `osd_deep_scrub_interval = 7_day`
- `osd_deep_scrub_randomize_ratio = 0.15`
- shallow scrub 的 `osd_scrub_min_interval = 1_day`
- `osd_scrub_interval_randomize_ratio = 0.5`，所以下一次 periodic scrub 候選時間會落在前次 scrub 後的 `[1, 1.5)` 天

pool 可用 `deep_scrub_interval` 覆寫 global／OSD 設定；[`PgScrubber::populate_config_params()`](https://github.com/ceph/ceph/blob/v19.2.2/src/osd/scrubber/pg_scrubber.cc#L657-L700) 會先讀 pool option，值不大於 0 才回退到 `osd_deep_scrub_interval`。

### 2. 未滿 7 天也可能提前 deep scrub

[`PG::is_time_for_deep()`](https://github.com/ceph/ceph/blob/v19.2.2/src/osd/PG.cc#L1418-L1479) 有兩條自動升級路徑：

1. `now >= last_deep_scrub_stamp + osd_deep_scrub_interval` 時，該次 scrub 必須變成 deep scrub。
2. 還沒到 7 天時，每次允許 shallow scrub 的機會有 `15%` 機率升級成 deep scrub。

這個 15% 是把工作攤開，避免所有 PG 在同一天形成 scrub wave。它也表示「7 天」是到期門檻，不是每個 PG 精準固定七天才跑一次。

依上述原始碼定義的隨機過程做模型（每 1～1.5 天一個候選、每次 15% 提前升級、滿 7 天後下一個候選強制 deep），在沒有 queue delay 的假設下，單一 PG 的長期平均 deep scrub 間隔約 **5.22 天**。這是本研究的機率模型結果，不是 Ceph SLA；它代表實際需要的平均 scrub 工作量可能高於單純 `PG / 7 days`：

| PG 數 | 7 天最低規劃率 | 依預設隨機過程推估的長期平均率 |
|---:|---:|---:|
| 2048 | 292.6 PG/day | 約 392.0 PG/day |
| 4096 | 585.1 PG/day | 約 784.0 PG/day |

### 3. 為什麼理想 scheduling 尾端可能到 8.5 天

[`ScrubQueue::adjust_target_time()`](https://github.com/ceph/ceph/blob/v19.2.2/src/osd/scrubber/osd_scrub_sched.cc#L276-L314) 會把下一個 periodic scrub 候選排在前次 scrub 後的 1～1.5 天。若某 PG 在接近第 7 天前剛完成一次 shallow scrub且沒有抽中 15% 升級，下一個候選最晚可到約第 8.5 天；屆時 `PG::is_time_for_deep()` 才會因超過 7 天而強制升級。

這個 8.5 天只是一個忽略 tick backoff、queue 與執行時間的 scheduling 包絡，而且指的是「取得 deep scrub 候選機會」，不是「已經讀完資料」。實際上，job 可因 OSD 資源、recovery、PG 狀態、時間窗或 queue backlog 繼續延後；開始後還要再加上該 PG 真正 deep scrub 的 I/O 時間。

## 為什麼 PG 數不足以算 wall-clock time

### deep scrub 讀的是資料，不只是數 PG

Ceph 官方文件說明，deep scrub 會建立 PG 內 object catalog，並比較 primary 和 replica 的 object 內容；shallow scrub 才只比 metadata。[Placement Groups — Scrub a PG](https://docs.ceph.com/en/squid/rados/operations/placement-groups/#scrub-a-pg)

因此粗略的實體讀取量為：

```text
replicated pool: physical_bytes_to_scan ≈ logical_stored_bytes × pool_size
EC pool:         physical_bytes_to_scan ≈ logical_stored_bytes × EC_overhead
```

還要加上 object metadata、omap、checksum 與跨 OSD 比對成本。相同 2048 PG，100 GiB pool 與 1 PiB pool 不可能有相同執行時間。

例如 1 PiB logical、`size=3` 的 replicated pool，要在 7 天內掃完，光是資料讀取的 cluster 平均速率下限就約 **5.2 GiB/s**，尚未計入額外成本。這個數字與 PG 是 2048 或 4096 無直接關係；PG 數主要改變每個 PG 的平均大小與 scheduling／metadata overhead。

### 自動 scrub 會被環境條件擋住

[`OsdScrub::restrictions_on_scrubbing()`](https://github.com/ceph/ceph/blob/v19.2.2/src/osd/scrubber/osd_scrub.cc#L155-L196) 顯示 periodic scrub 會受這些條件影響：

- OSD 是否已有太多 scrub；
- 每個 tick 預設有 66% backoff 機率；
- recovery 進行中且 `osd_scrub_during_recovery=false`（預設）；
- scrub 允許的 hour／weekday；
- load threshold 與 job deadline。

此外，官方 health 文件明確說只有 clean PG 才會收到 deep scrub；degraded／misplaced PG 可能不能執行。[PG_NOT_DEEP_SCRUBBED](https://docs.ceph.com/en/squid/rados/operations/health-checks/#pg-not-deep-scrubbed)

### OSD 拓樸與 QoS 決定實際吞吐量

19.2.2 的設定檔把 `osd_max_scrubs` 預設定為 3，但同一份版本 metadata 錯誤註記 mClock 下忽略此設定。[`osd_max_scrubs`](https://github.com/ceph/ceph/blob/v19.2.2/src/common/options/osd.yaml.in#L190-L198) 可執行原始碼沒有 mClock 例外：[`ScrubResources`](https://github.com/ceph/ceph/blob/v19.2.2/src/osd/scrubber/scrub_resources.cc#L25-L58) 仍限制每個 OSD 同時擔任 primary 的 periodic scrub 數小於 3，replica reservation 也以 3 建立，runtime 修改會更新上限。19.2.3 刪除了錯誤 note，但沒有改掉這段 enforcement。

所以 `3 × OSD 數` 只能當 primary scrub concurrency 的理論上限；每個 scrub 還要取得 replica reservation，CRUSH 分布不均時有效 concurrency 會更低，不能直接拿理論上限當 production 吞吐量。若有 `M` 個 OSD、每個 PG 有 `r` 個 acting shard，且分布完全均勻，單看 reservation 的樂觀上限為：

```text
C_cap <= floor(min(3M, 3M / (r - 1)))
```

例如 9 OSD、replicated `size=3`，樂觀上限是 `floor(27/2)=13` 個同時 scrub；這還沒扣掉 CRUSH 不均、其他 pool、慢 OSD 與 mClock 競爭。若硬套這個樂觀上限，要在 7 天內跟上，代表性 PG 的平均完整 deep scrub duration 必須低於：

- 2048 PG：約 64 分鐘；
- 4096 PG：約 32 分鐘。

這只是 admission check，不是 ETA；有效 concurrency 通常低於 13。

預設 mClock `balanced` profile 將 scrub 類工作放在 `background_best_effort`，reservation 為 0、weight 為 1、limit 為 90%。[`mClockScheduler.cc`](https://github.com/ceph/ceph/blob/v19.2.2/src/osd/scheduler/mClockScheduler.cc#L359-L373) 這代表 scrub 沒有保證的最低份額；client／recovery 壓力、OSD capacity model 與媒體效能都會改變實際完成率。mClock 下 `osd_scrub_sleep` 也會被強制改成 0。[`OSD::maybe_override_sleep_options_for_qos()`](https://github.com/ceph/ceph/blob/v19.2.2/src/osd/OSD.cc#L10227-L10253)

## 可直接套用的估算公式

令：

- `P`：pool PG 數；
- `S`：replicated pool 的 `size`，或 EC 平均 shard 數；
- `O`：承載此 pool 的 OSD 數；
- `D_pg`：在你的環境中，一個代表性 PG deep scrub 的平均 elapsed time；
- `C_eff`：考慮 primary／replica reservation、CRUSH 分布、mClock 與負載後的有效同時 scrub 數。

則一批全部 PG 的純工作時間可粗估為：

```text
T_work ≈ P × D_pg / C_eff
```

或從實體讀取吞吐量估算：

```text
T_work ≈ physical_bytes_to_scan / measured_aggregate_deep_scrub_read_bandwidth
```

自動週期的 calendar time 則是：

```text
T_auto ≈ max(scheduling 分散週期, queue 消化工作所需時間)
```

在預設且容量足夠時，可用 7 天當 scheduling budget；同步起點的 toy model 會讓最後一個 PG 在接近 8.5 天時才取得候選機會，之後仍須加上 queue 與 I/O 時間。若 `T_work` 大於這個週期，queue 會逐輪累積，完成時間不再有有限上界。

另外，預設 `PG_NOT_DEEP_SCRUBBED` 並不是第 7 天立刻告警。19.2.2 的 `mon_warn_pg_not_deep_scrubbed_ratio` 預設為 `0.75`，monitor 的 cutoff 是 `interval × (1 + ratio)`，所以預設約在 **12.25 天**才告警。[設定值](https://github.com/ceph/ceph/blob/v19.2.2/src/common/options/global.yaml.in#L1759-L1767)／[判斷公式](https://github.com/ceph/ceph/blob/v19.2.2/src/mon/PGMap.cc#L3293-L3314) 沒有告警不等於一定有達成 7 天目標。

## 如何量出你這個 cluster 的答案

先做 read-only 設定盤點：

```bash
ceph config get osd osd_deep_scrub_interval
ceph config get osd osd_scrub_min_interval
ceph config get osd osd_scrub_interval_randomize_ratio
ceph config get osd osd_deep_scrub_randomize_ratio
ceph config get osd osd_scrub_during_recovery
ceph config get osd osd_max_scrubs
ceph config get osd osd_op_queue
ceph config get osd osd_mclock_profile
ceph osd pool get <pool> pg_num
ceph osd pool get <pool> size
ceph osd pool get <pool> deep_scrub_interval
ceph osd dump | grep -E 'noscrub|nodeep-scrub'
```

再保存 pool 內每個 PG 的基線：

```bash
ceph pg ls-by-pool <pool> -f json \
  | jq '[.pg_stats[] | {
      pgid,
      state,
      last_deep_scrub_stamp,
      last_scrub_duration,
      objects: .stat_sum.num_objects,
      bytes: .stat_sum.num_bytes,
      acting
    }]' > pg-deep-scrub-baseline.json
```

`last_deep_scrub_stamp` 是最重要的完成證據；這個欄位由 [`pg_stat_t::dump()`](https://github.com/ceph/ceph/blob/v19.2.2/src/osd/osd_types.cc#L2861-L2880) 匯出。`last_scrub_duration` 只代表最近一次 scrub，最近一次若是 shallow scrub，就不能直接當作 deep scrub duration。

要得到實際「全 pool 一輪」時間，必須定期保存同一份 PG snapshot，直到全部 PG 的 `last_deep_scrub_stamp` 都晚於基線值。這比看 `ceph -s` 當下有幾個 `scrubbing+deep` 準確，因為後者只是瞬間 concurrency，不是完成 ledger。

`last_scrub_duration` 只有在同一筆資料的 `last_scrub_stamp == last_deep_scrub_stamp` 時，才可安全視為最近一次 deep scrub duration sample；否則它可能是較新的 shallow scrub。收集多個這類 sample 的平均值 `D_pg` 後，才能代入前述公式。另可用 `ceph daemon osd.<id> dump_scrubs` 看 scheduler queue，用 `dump_scrub_reservations` 看 local／remote reservation，並以 `ceph daemon osd.<id> perf dump` 查 `osd_scrub_dp_repl` 或 `osd_scrub_dp_ec` 的 elapsed／preemption counter。

## 版本邊界

Ceph 19.2.3 新增了 `osd_deep_scrub_interval_cv`，改動 deep scrub interval 的 randomization 語意；不能把 19.2.3／較新版本的常態分布說明倒套到 19.2.2。本報告所有 scheduling 判斷均以 `v19.2.2` tag 為準。

## 最後判斷

若目前只知道 `2048 / 4096 PG`：

- 對外可說的合理規劃值是：**兩者都以 7 天為 scheduling budget；8.5 天只是一個忽略 backoff／queue／I/O 的候選機會包絡，不是 production 完成 ETA。**
- 4096 PG 不是自動變成 14 天，而是要求兩倍 PG 完成率；若 logical bytes 不變，scan bytes 大致不變。固定 overhead 或 cluster 吞吐量不足時才會拖長。
- 要報一個小時級或天級的真實數字，至少還需要：pool logical bytes／objects、`size` 或 EC profile、OSD 數與媒體、目前設定、以及代表性 deep scrub 的實測 duration／讀取 throughput。
