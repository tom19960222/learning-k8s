## 結論（一句話）

**在 KubeVirt v1.6.4 上，「最低網路延遲」與「一定能 live migration」這兩個目標的交集比多數人以為的窄：能同時滿足兩者的槓桿只有四個 —— `masquerade` 改 `bridge`（加 annotation）、`networkInterfaceMultiqueue`、`dedicatedCpuPlacement` + `isolateEmulatorThread`、以及 hugepages；而 SR-IOV、`hypervPassthrough`、`evmcs`、`hostDevices` 全都會讓 VM 失去乾淨的可遷移性。virtio-net RSS（Windows vRSS 的硬體基礎）在 v1.6.4 根本沒有 API 可以開，即使用 sidecar 硬改 domain XML，在 vhost-net 路徑下也會被 QEMU 靜默關掉。**

## §2 網路資料路徑：virtio-net、vhost-net、multiqueue

### 2.1 KubeVirt 何時才寫出 `<driver name='vhost'>`

這是整份研究裡最容易被誤解的一段。**[SP]**

[`pkg/virt-launcher/virtwrap/converter/network.go#L63-L65`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/converter/network.go#L63-L65)：

```go
if queueCount := uint(CalculateNetworkQueues(vmi, ifaceType)); queueCount != 0 {
    domainIface.Driver = &api.InterfaceDriver{Name: "vhost", Queues: &queueCount}
}
```

而 `queueCount` 只有在 multiqueue 打開時才非 0 —— [`#L129-L149`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/converter/network.go#L129-L149)：

```go
func CalculateNetworkQueues(vmi *v1.VirtualMachineInstance, ifaceType string) uint32 {
	if ifaceType != v1.VirtIO {
		return 0
	}
	return NetworkQueuesCapacity(vmi)
}

func NetworkQueuesCapacity(vmi *v1.VirtualMachineInstance) uint32 {
	if !isTrue(vmi.Spec.Domain.Devices.NetworkInterfaceMultiQueue) {
		return 0
	}
	cpuTopology := vcpu.GetCPUTopology(vmi)
	queueNumber := vcpu.CalculateRequestedVCPUs(cpuTopology)
	if queueNumber > multiQueueMaxQueues { ... }
	return queueNumber
}
```

結論鏈：

- **`networkInterfaceMultiqueue: false`（預設）→ domain XML 完全沒有 `<driver>` 元素。** **[SP]**
- 沒有 `<driver name>` 時，libvirt 的行為是「有 vhost 就用 vhost，開不起來就靜默退回 qemu userspace，不報錯」——
  [`docs/formatdomain.rst#L5730-L5731`](https://gitlab.com/libvirt/libvirt/-/blob/v10.10.0/docs/formatdomain.rst#L5730)：
  > *If this attribute is not present, then the domain defaults to 'vhost' if present, but silently falls back to 'qemu' without error.* **[SP]**
- **所以：不開 multiqueue 並不代表沒有 vhost-net。** 預設就已經在走 vhost-net。這點與很多教學文的說法相反。**[INF]**

### 2.2 但 multiqueue 會把「靜默退回」變成「開機失敗」

libvirt 原始碼 [`src/qemu/qemu_interface.c#L192-L209`](https://gitlab.com/libvirt/libvirt/-/blob/v10.10.0/src/qemu/qemu_interface.c#L192)：

```c
for (i = 0; i < vhostfdSize; i++) {
    VIR_AUTOCLOSE fd = open(vhostnet_path, O_RDWR);
    if (fd < 0) {
        virDomainAuditNetDevice(vm->def, net, vhostnet_path, false);
        if (net->driver.virtio.name == VIR_DOMAIN_NET_DRIVER_TYPE_VHOST) {
            virReportError(VIR_ERR_CONFIG_UNSUPPORTED, "%s",
                           _("vhost-net was requested for an interface, but is unavailable"));
            return -1;              /* ← 硬錯誤 */
        }
        VIR_WARN(...);
        break;                      /* ← 靜默降級 */
    }
    ...
}
```

**[INF]**（由兩段 **[SP]** 組成）：開了 `networkInterfaceMultiqueue` → KubeVirt 明確寫 `name="vhost"` → 若 `/dev/vhost-net` 不可用，domain **啟動失敗**，而不是降級。

實務上 KubeVirt 會替有 virtio NIC 的 VMI 申請 `devices.kubevirt.io/vhost-net` device plugin 資源，所以正常情況下不會踩到 —— [`pkg/virt-controller/services/renderresources.go#L584-L590`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-controller/services/renderresources.go#L584)：

```go
if util.NeedVirtioNetDevice(vmi, allowEmulation) {
    // Note that about network interface, allowEmulation does not make
    // any difference on eventual Domain xml, but uniformly making
    // /dev/vhost-net unavailable and libvirt implicitly fallback
    // to use QEMU userland NIC emulation.
    res[VhostNetDevice] = resource.MustParse("1")
}
```

注意這段註解說的「implicitly fallback」**只在沒有明確 `name="vhost"` 時成立**。在 `allowEmulation`（software emulation）叢集上同時開 multiqueue，依 §2.2 的推論會是硬錯誤而非降級 —— 這是 KubeVirt 註解與 libvirt 實作之間的一個縫隙。**[INF]**，未實測 **[EXP]**。

### 2.3 佇列數怎麼算

`queues = sockets × cores × threads`，上限 256。**[SP]**

- [`converter/vcpu/vcpu.go#L26-L28`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/converter/vcpu/vcpu.go#L26-L28) — `CalculateRequestedVCPUs = Cores * Sockets * Threads`
- [`converter/converter.go#L73`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/converter/converter.go#L73) — `multiQueueMaxQueues = uint32(256)`

重要陷阱：`GetCPUTopology` 在**完全沒指定 topology** 時，會把 CPU limit／request 整包塞進 `sockets` —— [`vcpu.go#L292-L328`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/converter/vcpu/vcpu.go#L292)：

```go
if vmiCPU == nil || (vmiCPU.Cores == 0 && vmiCPU.Sockets == 0 && vmiCPU.Threads == 0) {
    resources := vmi.Spec.Domain.Resources
    if cpuLimit, ok := resources.Limits[k8sv1.ResourceCPU]; ok {
        sockets = uint32(cpuLimit.Value())
    } else if cpuRequests, ok := resources.Requests[k8sv1.ResourceCPU]; ok {
        sockets = uint32(cpuRequests.Value())
    }
}
```

**[SP]** 所以「不寫 topology」對 Windows 是有害的（見 §6.1）。本文的 YAML 一律明寫 topology。

### 2.4 沒有 RSS，multiqueue 為什麼還有效？

因為 RX 的佇列選擇是 **tap/tun 在 host 側依 flow hash 做的**，不需要 guest 協商 `VIRTIO_NET_F_RSS`。

本機 `linux` submodule（Ubuntu HWE 6.8，`6e81b9ec3`）`drivers/net/tun.c#L523-L542`：

```c
static u16 tun_automq_select_queue(struct tun_struct *tun, struct sk_buff *skb)
{
	struct tun_flow_entry *e;
	u32 txq = 0;
	u32 numqueues = READ_ONCE(tun->numqueues);

	txq = __skb_get_hash_symmetric(skb);
	e = tun_flow_find(&tun->flows[tun_hashfn(txq)], txq);
	if (e) {
		tun_flow_save_rps_rxhash(e, txq);
		txq = e->queue_index;
	} else {
		txq = ((u64)txq * numqueues) >> 32;
	}
	return txq;
}
```

**[SP]**（相對於該本機 ref）。這是 tun 長年穩定的機制，但**你節點的 kernel 版本必須自行確認** **[RT]**：

```bash
kubectl get nodes -o wide   # 看 KERNEL-VERSION 欄
```

**[INF]**：因此 multiqueue 在 Windows guest 上仍能把多條 flow 分散到多個 vCPU 處理，即使 §3 所述的 virtio-net RSS 完全不可用。單一 flow 的延遲不會因此改善 **[EXP]**。

## §3 RSS / vRSS：v1.6.4 的硬性天花板（負面結果）

這一節是整份研究最重要的「不能做」結論。

### 3.1 KubeVirt 沒有 API

virt-launcher 用來產生 domain XML 的 interface driver 結構只有三個欄位 —— [`pkg/virt-launcher/virtwrap/api/schema.go#L872-L876`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/api/schema.go#L872-L876)：

```go
type InterfaceDriver struct {
	Name   string `xml:"name,attr"`
	Queues *uint  `xml:"queues,attr,omitempty"`
	IOMMU  string `xml:"iommu,attr,omitempty"`
}
```

**[SP]** 沒有 `rss`、沒有 `rss_hash_report`、沒有 `rx_queue_size`／`tx_queue_size`、沒有 host/guest offload 子元素。全域 grep 該檔案也找不到任何 `rss` 字串。**在 v1.6.4 的 VM/VMI spec 裡沒有任何欄位可以開啟 virtio-net RSS 或調整 virtio ring 大小。**

### 3.2 libvirt 支援，但需要 QEMU 有 CAP_SYS_ADMIN

libvirt 10.10.0 本身支援 —— [`src/conf/domain_conf.c#L9376-L9383`](https://gitlab.com/libvirt/libvirt/-/blob/v10.10.0/src/conf/domain_conf.c#L9376)（解析）、[`#L24322-L24328`](https://gitlab.com/libvirt/libvirt/-/blob/v10.10.0/src/conf/domain_conf.c#L24322)（輸出）、[`src/qemu/qemu_command.c#L3696-L3697`](https://gitlab.com/libvirt/libvirt/-/blob/v10.10.0/src/qemu/qemu_command.c#L3696)（轉成 QEMU `rss=` / `hash=`）。**[SP]**

但 libvirt 自己的文件寫得很清楚 —— [`docs/formatdomain.rst#L5808-L5816`](https://gitlab.com/libvirt/libvirt/-/blob/v10.10.0/docs/formatdomain.rst#L5808)：

> *The `rss` option enables in-qemu/ebpf RSS for virtio NIC. RSS works with virtio and tap backends only. Virtio NIC will be launched with "rss" property. For now "in-qemu" RSS is supported by libvirt. **QEMU may load eBPF RSS if it has CAP_SYS_ADMIN permissions, which is not supported by default in libvirt.*** **[SP]**

### 3.3 而 in-qemu（software）RSS 在 vhost-net 下不存在

QEMU 9.1.0 `hw/net/virtio-net.c#L1284-L1297`：

```c
static void virtio_net_commit_rss_config(VirtIONet *n)
{
    if (n->rss_data.enabled) {
        n->rss_data.enabled_software_rss = n->rss_data.populate_hash;
        if (n->rss_data.populate_hash) {
            virtio_net_detach_epbf_rss(n);
        } else if (!virtio_net_attach_epbf_rss(n)) {
            if (get_vhost_net(qemu_get_queue(n->nic)->peer)) {
                warn_report("Can't load eBPF RSS for vhost");     /* ← 沒有 fallback */
            } else {
                warn_report("Can't load eBPF RSS - fallback to software RSS");
                n->rss_data.enabled_software_rss = true;
            }
        }
    ...
```

更關鍵的是特徵協商階段就先關掉了 —— [`#L794-L800`](https://github.com/qemu/qemu/blob/v9.1.0/hw/net/virtio-net.c#L794)：

```c
    if (!get_vhost_net(nc->peer)) {
        return features;
    }
    if (!ebpf_rss_is_loaded(&n->ebpf_rss)) {
        virtio_clear_feature(&features, VIRTIO_NET_F_RSS);
    }
```

且 `rss` / `hash` 兩個 property 預設都是 `false` —— [`#L3957-L3960`](https://github.com/qemu/qemu/blob/v9.1.0/hw/net/virtio-net.c#L3957)。**[SP]**

### 3.4 綜合結論 **[INF]**

| 路徑 | 結果 |
|---|---|
| VM spec 直接開 RSS | **不可能**，無此欄位 **[SP]** |
| sidecar hook 改 domain XML 加 `<driver rss='on'/>` + 走 vhost-net（預設） | eBPF RSS 因缺 CAP_SYS_ADMIN 載不起來 → `VIRTIO_NET_F_RSS` 在協商時被清掉 → guest 根本看不到 RSS |
| sidecar 加 `rss='on'` 且強制 `name='qemu'`（關 vhost） | 可得 software RSS，但退出 vhost-net 核心快速路徑，**延遲幾乎必然變差**，與目標矛盾 |

**因此：在 KubeVirt v1.6.4 上，把「Windows vRSS」當成延遲優化手段是走不通的。可用的並行化手段只有 §2.4 的 tap 多佇列。** 請把預算放在 §4（binding）與 §6（CPU 隔離）。

> Windows guest 端 NetKVM 對「無 `VIRTIO_NET_F_RSS`、但有多佇列」的實際佇列使用行為，我**沒有** virtio-win 原始碼可讀 → **[UNV]**。待查來源見 §9。

## §4 Pod network binding：延遲最大的單一槓桿

### 4.1 masquerade 的成本是 NAT + conntrack

`masquerade` 會在 pod netns 建立完整的 nftables `nat` 表 —— [`pkg/network/setup/netpod/masquerade/masquerade.go#L108-L137`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/network/setup/netpod/masquerade/masquerade.go#L108)：

```go
m.nftable.AddTable(family, natTable)
m.nftable.AddChain(family, natTable, preroutingChain,  "{ type nat hook prerouting priority -100; }")
m.nftable.AddChain(family, natTable, inputChain,       "{ type nat hook input priority 100; }")
m.nftable.AddChain(family, natTable, outputChain,      "{ type nat hook output priority -100; }")
m.nftable.AddChain(family, natTable, postroutingChain, "{ type nat hook postrouting priority 100; }")
...
m.nftable.AddRule(family, natTable, postroutingChain, string(family), "saddr", guestIP, "counter", "masquerade")
```

之後每個 port 再加 DNAT／SNAT 規則（[`#L182-L214`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/network/setup/netpod/masquerade/masquerade.go#L182)）。**[SP]**

`bridge` binding 沒有這些：它是 pod netns 內的純 L2 bridge，封包不進 nat hook、不建 conntrack 條目。**[INF]**

實際延遲差值 **[EXP]** —— 本文不給數字，量測方法見 §12。

### 4.2 但 bridge + pod network 預設**不能**遷移

[`pkg/network/vmispec/interface.go#L57-L76`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/network/vmispec/interface.go#L57)：

```go
func VerifyVMIMigratable(vmi *v1.VirtualMachineInstance, bindingPlugins map[string]v1.InterfaceBindingPlugin) error {
	ifaces := vmi.Spec.Domain.Devices.Interfaces
	if len(ifaces) == 0 {
		return nil
	}

	_, allowPodBridgeNetworkLiveMigration := vmi.Annotations[v1.AllowPodBridgeNetworkLiveMigrationAnnotation]
	if allowPodBridgeNetworkLiveMigration && IsPodNetworkWithBridgeBindingInterface(vmi.Spec.Networks, ifaces) {
		return nil
	}
	if IsPodNetworkWithMasqueradeBindingInterface(vmi.Spec.Networks, ifaces) ||
		IsPodNetworkWithMigratableBindingPlugin(vmi.Spec.Networks, ifaces, bindingPlugins) {
		return nil
	}

	return fmt.Errorf(
		"cannot migrate VMI which does not use masquerade, bridge with %s VM annotation or a migratable plugin to connect to the pod network",
		v1.AllowPodBridgeNetworkLiveMigrationAnnotation,
	)
}
```

**[SP]** 解法就是加上 annotation：

```yaml
kubevirt.io/allow-pod-bridge-network-live-migration: "true"
```

annotation 常數定義在 [`staging/src/kubevirt.io/api/core/v1/types.go#L1336-L1338`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/staging/src/kubevirt.io/api/core/v1/types.go#L1336)。程式碼只檢查 **key 是否存在**，不檢查值（`_, ok := vmi.Annotations[...]`）**[SP]**。

> **附帶發現 [SP]：** [`#L94-L101`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/network/vmispec/interface.go#L94) 的 `IsPodNetworkWithMasqueradeBindingInterface` 在**找不到 pod network 時 `return true`**。也就是說「只有 multus secondary network、完全沒有 pod network」的 VMI 在網路面被視為可遷移。這是設計如此，但容易被誤讀成「masquerade 才行」。

### 4.3 選擇建議

| binding | 延遲 | 可遷移 | 建議 |
|---|---|---|---|
| `masquerade`（預設） | 較差（NAT + conntrack）**[INF]** | 直接可以 **[SP]** | 保守起手式 |
| `bridge` + annotation | 較好 **[INF]** | 可以，但需 annotation **[SP]** | **本文推薦**；代價是失去 pod IP 語意與部分 Service 整合，需自行驗證 **[EXP]** |
| binding plugin | 視 plugin 的 `Migration` 欄位而定 **[SP]**（[`#L78-L92`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/network/vmispec/interface.go#L78)） | 需 plugin 宣告 | 需額外部署，不在本文保守範圍 |
| SR-IOV | 最好 | **有嚴重代價**，見 §5 | **不建議**（本題要求 live migration） |

## §5 SR-IOV / hostdev 與 live migration

### 5.1 `hostDevices` 與 `gpus` 是硬性阻擋

[`pkg/virt-handler/vm.go#L1198-L1200`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-handler/vm.go#L1198) 與 [`#L1232-L1234`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-handler/vm.go#L1232)：

### 5.2 但 `interfaces[].sriov` **不在**這個清單裡

注意 `vmiContainsPCIHostDevice` **沒有**檢查 `interfaces[].sriov`。SR-IOV NIC 走的是另一條路：**遷移前把 VF 熱插拔掉**。

[`pkg/virt-launcher/virtwrap/live-migration-source.go#L1097-L1101`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/live-migration-source.go#L1097)：

```go

// on the source domain just before migration
func prepareDomainForMigration(virtConn cli.Connection, domain cli.VirDomain) error {
	return hotUnplugHostDevices(virtConn, domain)
}
```

`hotUnplugHostDevices` → `sriov.SafelyDetachHostDevices`，等待 `DomainEventDeviceRemoved`，逾時 30 秒（[`#L124-L143`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/live-migration-source.go#L124)）。目標端再由 `HotplugHostDevices` 熱插回來（[`pkg/virt-launcher/virtwrap/manager.go#L580-L597`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/manager.go#L580)）。`SRIOVLiveMigration` feature gate 已是 GA、恆為 true（[`pkg/virt-config/featuregate/inactive.go#L102`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-config/featuregate/inactive.go#L102)）。**[SP]**

### 5.3 為什麼本文仍然不建議 SR-IOV

**KubeVirt v1.6.4 完全沒有 virtio-net failover／standby（`VIRTIO_NET_F_STANDBY`）支援。** 對 `pkg/` 與 `staging/src/kubevirt.io/api/` 全域 grep `failover|standby|teaming` **零命中** **[SP]**。而 QEMU 9.1.0 是有這個能力的（`hw/net/virtio-net.c` 的 `failover_find_primary_device` 等，[`#L880-L924`](https://github.com/qemu/qemu/blob/v9.1.0/hw/net/virtio-net.c#L880)）**[SP]** —— 也就是 KubeVirt 沒有把它接出來。

**[INF]** 推論：SR-IOV VMI 遷移時，VF 被拔掉到目標端插回來之間，**該介面沒有任何自動接手的備援 NIC**，網路會中斷。要無縫就得在 Windows guest 內自建 NIC teaming，而且要能承受 PCI 熱移除 —— 這已超出「保守可用」的範圍，且 Windows guest 側行為 **[UNV]**。

**結論：本題要求「必須支援 live migration」，就不要用 SR-IOV。**

## §6 CPU、NUMA、hugepages

### 6.1 明寫 topology

如 §2.3 所述，不寫 topology 會讓 `sockets = vCPU 總數`。對 Windows 這是雙重問題：

- Windows Server 2022 的 socket 授權／版本限制 **[UNV]**（需查 Microsoft 授權文件，見 §9）
- 多 socket 會讓 guest 看到多個 NUMA node（若同時開 NUMA），排程行為改變 **[INF]**

`dedicatedCpuPlacement` 下 `threads > 2` 會被 webhook 擋 —— [`pkg/virt-api/webhooks/validating-webhook/admitters/vmi-create-admitter.go#L802-L815`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-api/webhooks/validating-webhook/admitters/vmi-create-admitter.go#L802)。**[SP]**

### 7.4 其他 hyperv 功能也會加 nodeSelector

[`nodeselectorrenderer.go#L178-L195`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-controller/services/nodeselectorrenderer.go#L178) 會為每個啟用的 hyperv 功能加上 `hyperv.node.kubevirt.io/<feature>: "true"` 的 nodeSelector。**[SP]**

VPIndex, SyNIC: depend on both MSR and capability. IPI, TLBFlush: depend on KVM Capabilities. Runtime, Reset, SyNICTimer, Frequencies, Reenlightenment: depend on KVM MSRs availability.*

**[INF]** 這正好給出「最安全的 Hyper-V 子集」：`relaxed` + `vapic` + `spinlocks` 三者不加 nodeSelector 限制（因為 `makeHVFeatureLabelTable` 的表裡沒有它們，見 [`#L225-L240`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-controller/services/nodeselectorrenderer.go#L225) 之後的完整表），因此對遷移最友善。這也正是 KubeVirt 官方 Windows 範例採用的組合 —— [`examples/vmi-windows.yaml`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/examples/vmi-windows.yaml)：

```yaml
features:
  acpi: {}
  apic: {}
  hyperv:
    relaxed: {}
    spinlocks:
      spinlocks: 8191
    vapic: {}
  smm: {}
```

> **注意 [SP]：** 官方範例用的是 `model: e1000`，**不是 virtio**。這是為了免驅動開機，不是效能建議。本文 YAML 改用 virtio（見 §10 的驅動前提）。

這是一個容易被誤以為存在的設定。對 `pkg/` 與 `staging/` 全域 grep `Downtime`，**唯一命中是 log 字串**（[`live-migration-source.go#L737-L742`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/live-migration-source.go#L737)）：


**KubeVirt 從不呼叫 `virDomainMigrateSetMaxDowntime`。** **[SP]**

實際傳給 libvirt 的參數只有這些 —— [`#L837-L850`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/live-migration-source.go#L837)：

```go

    URI: migrURI, URISet: true,
```

**[INF]** 所以 downtime 是**間接**控制的：透過 `completionTimeoutPerGiB` 決定何時「出手幫忙」，再由 auto-converge／post-copy／暫停三選一收斂。

### 8.3 收斂機制的實際邏輯

migration flags —— [`#L98-L122`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/live-migration-source.go#L98)：**[SP]**

```go
migrateFlags := libvirt.MIGRATE_LIVE | libvirt.MIGRATE_PEER2PEER | libvirt.MIGRATE_PERSIST_DEST
if isBlockMigration       { migrateFlags |= libvirt.MIGRATE_NON_SHARED_INC }
if options.UnsafeMigration{ migrateFlags |= libvirt.MIGRATE_UNSAFE }
if options.AllowAutoConverge { migrateFlags |= libvirt.MIGRATE_AUTO_CONVERGE }
if options.AllowPostCopy     { migrateFlags |= libvirt.MIGRATE_POSTCOPY }
```

逾時門檻 —— [`#L454-L489`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/live-migration-source.go#L454)：**[SP]**

```go
acceptableCompletionTime: options.CompletionTimeoutPerGiB * getVMIMigrationDataSize(vmi, l.ephemeralDiskDir),
...
func (m *migrationMonitor) shouldTriggerTimeout(elapsed int64) bool {
	if m.acceptableCompletionTime == 0 { return false }
	return elapsed/int64(time.Second) > m.acceptableCompletionTime
}
func (m *migrationMonitor) shouldAssistMigrationToComplete(elapsed int64) bool {
	return m.shouldTriggerTimeout(elapsed) && m.options.AllowWorkloadDisruption
}
```

分支決策 —— [`#L560-L631`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-launcher/virtwrap/live-migration-source.go#L560)：**[SP]**

| 條件 | 動作 |
|---|---|
| 已在 post-copy | 什麼都不做（中止會遺失狀態） |
| 逾時 **且** `allowWorkloadDisruption` **且** `allowPostCopy` | `MigrateStartPostCopy(0)` |
| 逾時 **且** `allowWorkloadDisruption` **且** 不允許 post-copy | `dom.Suspend()` 暫停 guest，並把 `acceptableCompletionTime *= 2` |
| `progressTimeout` 內零進度 | `AbortJob()`，訊息 `Live migration stuck for %d seconds` |
| 逾時但 `allowWorkloadDisruption` 為 false | `AbortJob()`，訊息 `Live migration is not completed after %d seconds` |

**[INF]** 對 Windows 的意涵：Windows Server 2022 idle 時 dirty rate 通常不高，預設 `150 s/GiB` 相當寬鬆。真正的風險是**記憶體寫入密集**的工作負載會一直逾時被 abort。若不能接受 abort，就要在 `allowWorkloadDisruption + allowPostCopy`（有 network failure 導致 VM crash 的風險，[`types.go#L3104-L3108`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/staging/src/kubevirt.io/api/core/v1/types.go#L3104) 明講）與 `allowWorkloadDisruption` 單開（暫停 guest，可預期的停機）之間選一個。**本文保守建議選後者。**

### 8.4 MigrationPolicy 只能調 5 個欄位

[`staging/src/kubevirt.io/api/migrations/v1alpha1/types.go#L43-L56`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/staging/src/kubevirt.io/api/migrations/v1alpha1/types.go#L43)：**[SP]**

```go
type MigrationPolicySpec struct {
	Selectors *Selectors `json:"selectors"`
	AllowAutoConverge       *bool              `json:"allowAutoConverge,omitempty"`
	BandwidthPerMigration   *resource.Quantity `json:"bandwidthPerMigration,omitempty"`
	CompletionTimeoutPerGiB *int64             `json:"completionTimeoutPerGiB,omitempty"`
	AllowPostCopy           *bool              `json:"allowPostCopy,omitempty"`

```

**`progressTimeout`、`parallelMigrationsPerCluster`、`network`、`disableTLS` 不能用 MigrationPolicy 覆寫**，只能在 KubeVirt CR 的 `configuration.migrations` 設定。這是常見誤解。

### 8.5 遷移專用網路

`MigrationConfiguration.Network` —— [`types.go#L3117-L3119`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/staging/src/kubevirt.io/api/core/v1/types.go#L3117)：

> *Network is the name of the CNI network to use for live migrations. By default, migrations go through the pod network.*

**[INF]** 把遷移流量移出 pod network，可避免遷移期間排擠 VM 的資料流量、間接保護延遲。這是**叢集層級**設定，不在 VM YAML 內。

### 8.6 `host-model` 對遷移目標的限制

預設 CPU model 就是 `host-model` —— [`schema.go#L36-L38`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/staging/src/kubevirt.io/api/core/v1/schema.go#L36)：

```go
CPUModeHostPassthrough = "host-passthrough"
CPUModeHostModel       = "host-model"
DefaultCPUModel        = CPUModeHostModel
```

**[SP]** 遷移時 KubeVirt 會把**來源 node 的 host CPU model** 轉成目標 pod 的 nodeSelector —— [`pkg/virt-controller/watch/migration/migration.go#L2243-L2293`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-controller/watch/migration/migration.go#L2243)：

```go
nodeSelectorKeyForHostModel = virtv1.SupportedHostModelMigrationCPU + hostCpuModel
result[nodeSelectorKeyForHostModel] = hostModelLabelValue
```

且第一次遷移後只保留 `CPUFeatureLabel` / `SupportedHostModelMigrationCPU` 類的 key，避免「遷過去就回不來」（[`#L2246-L2264`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-controller/watch/migration/migration.go#L2246) 的註解明講）。**[SP]**

若 node 完全沒有 host CPU model label，`isHostModelMigratable` 會讓 VMI 不可遷移 —— [`vm.go#L2405-L2414`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-handler/vm.go#L2405)。**[SP]**

**[INF]** 異質 CPU 叢集要遷移，就得放棄 `host-model`，改指定一個所有 node 都支援的具名 model（例如 `Nehalem`、`Skylake-Server`）。代價是失去部分 CPU 指令集。**這是本文 YAML 留給你決定的唯一開放項** —— 見 §10 的註解。

### 8.7 完整的「不可遷移」清單

[`pkg/virt-handler/vm.go#L1186-L1230`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-handler/vm.go#L1186) 的判斷順序，這是唯一權威來源 **[SP]**：

1. `checkNetworkInterfacesForMigration` → pod network binding 不合格（§4.2）
2. `isHostModelMigratable` → node 缺 host CPU model label（§8.6）
3. `vmiContainsPCIHostDevice` → `hostDevices` 或 `gpus` 非空（§5.1）
4. `util.IsSEVVMI` → 用了 SEV
5. `util.IsSecureExecutionVMI` → 用了 Secure Execution（s390x）
6. `reservation.HasVMIPersistentReservation` → SCSI persistent reservation
7. TSC frequency 需求未滿足（§7.3b）
8. `hypervPassthrough`（§7.3a）
9. `checkVolumesForMigration` 的 `blockErr` → PVC 非 RWX（[`#L1727-L1760`](https://github.com/kubevirt/kubevirt/blob/v1.6.4/pkg/virt-handler/vm.go#L1727)）

**所有 PVC 必須是 ReadWriteMany**，否則錯誤訊息是
`cannot migrate VMI: PVC %v is not shared, live migration requires that all PVCs must be shared (using ReadWriteMany access mode)`。**[SP]**

## §10 保守可用的完整 VM YAML

### 設計原則

1. 只用 §1–§8 中 **[SP]** 證明過、且不會讓 `LiveMigratable` 變成 `False` 的設定。
2. 每個非預設值都對應本文的一個章節。
3. 分成**兩段**：Tier A（無前置條件，直接可套用）與 Tier B（需叢集能力，另附檢查指令）。

### Tier A —— 直接可用（不需要任何叢集特殊設定）

```yaml
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: win2022-lowlat
  namespace: default
spec:
  runStrategy: Always
  template:
    metadata:
      labels:
        kubevirt.io/vm: win2022-lowlat
        # 供 MigrationPolicy 的 virtualMachineInstanceSelector 挑選（§8.4）
        migration-tier: windows-lowlat
      annotations:
        # §4.2：允許 pod network 使用 bridge binding 仍可 live migration。
        # 程式碼只檢查 key 是否存在，值不重要。
        kubevirt.io/allow-pod-bridge-network-live-migration: "true"
    spec:
      # §8.6：預設就是 host-model，這裡明寫以示意圖。
      # 異質 CPU 叢集請改成所有 node 都支援的具名 model，例如 "Skylake-Server"。
      domain:
        cpu:
          model: host-model
          # §2.3 + §6.1：一定要明寫 topology，否則 sockets = vCPU 總數。
          sockets: 1
          cores: 4
          threads: 1
        memory:
          guest: 8Gi

        # §7.4：只用不需要 host kernel 支援、因此不加 nodeSelector 的三個
        # enlightenment，對遷移最友善。刻意不開 reenlightenment / evmcs /
        # hypervPassthrough（§7.3）。
        features:
          acpi: {}
          apic: {}
          smm: {}
          hyperv:
            relaxed: {}
            vapic: {}
            spinlocks:
              spinlocks: 8191

        # §7.1：Windows 用 hypervclock；關閉 hpet 以免 timer 干擾。
        clock:
          utc: {}
          timer:
            hpet:
              present: false
            pit:
              tickPolicy: delay
            rtc:
              tickPolicy: catchup
            hyperv: {}

        firmware:
          bootloader:
            efi:
              secureBoot: true

        devices:
          tpm: {}
          # §2.1 + §2.3：開 multiqueue → 寫出 <driver name='vhost' queues='4'/>
          # queues = sockets*cores*threads = 4
          networkInterfaceMultiqueue: true
          interfaces:
            - name: default
              # §4：bridge 延遲優於 masquerade，配合上面的 annotation 才可遷移
              bridge: {}
              # 預設就是 virtio（GetInterfaceType），明寫以免誤解
              model: virtio
          disks:
            - name: rootdisk
              disk:
                # 注意：amd64 的預設 disk bus 是 SATA（pkg/defaults/amd64.go），
                # 用 virtio 需要 guest 已安裝 virtio-blk 驅動。
                bus: virtio

        resources:
          requests:
            memory: 8Gi
            cpu: "4"
          limits:
            memory: 8Gi
            cpu: "4"

      networks:
        - name: default
          pod: {}

      volumes:
        - name: rootdisk
          persistentVolumeClaim:
            # §8.7 第 9 點：live migration 要求所有 PVC 都是 ReadWriteMany
            claimName: win2022-root-rwx

      terminationGracePeriodSeconds: 180
```

### Tier B —— 加上 CPU 隔離與 hugepages（需前置條件）

在 Tier A 的基礎上，把 `domain.cpu`、`domain.memory`、`resources` 換成：

```yaml
      domain:
        cpu:
          model: host-model
          sockets: 1
          cores: 4
          threads: 1
          # §6.2：需要 CPUManager feature gate（v1.6.4 仍是 Alpha）
          #       + kubelet static CPU manager policy
          #       會加上 nodeSelector cpumanager=true
          dedicatedCpuPlacement: true
          # §6.3：必須與 dedicatedCpuPlacement 併用；pod 會多要 1 顆 pCPU
          isolateEmulatorThread: true
          # 刻意不設 numa.guestMappingPassthrough（§6.4）

        memory:
          guest: 8Gi
          # §6.5：pod 會改成 request hugepages-2Mi: 8Gi
          hugepages:
            pageSize: 2Mi

        resources:
          requests:
            memory: 8Gi
            cpu: "4"     # §6.2：必須是整數且 request == limit
          limits:
            memory: 8Gi
            cpu: "4"     # 實際 pod 會是 5（4 + 1 emulator thread，§6.3）
```

**[RT]** 套用 Tier B 前必須全部通過：

```bash

kubectl describe node <node> | grep -A5 'Allocated resources'
```

### 搭配的 MigrationPolicy

```yaml
apiVersion: migrations.kubevirt.io/v1alpha1
kind: MigrationPolicy
metadata:
  name: windows-lowlat
spec:
  selectors:
    virtualMachineInstanceSelector:
      migration-tier: windows-lowlat
  # §8.3：逾時後暫停 guest 讓遷移收斂，而不是直接 abort。
  # 停機可預期，優於 post-copy 的 crash 風險。
  allowWorkloadDisruption: true
  allowPostCopy: false
  # §8.1：預設 150 s/GiB。8 GiB → 1200 s。這裡收緊到 8 GiB → 480 s。
  completionTimeoutPerGiB: 60
  # §8.1：0 代表不限速。若遷移會排擠 VM 流量，改成具體值。
  bandwidthPerMigration: 0Mi
  allowAutoConverge: true
```

> `allowAutoConverge: true` 的代價是 QEMU 會節流 guest vCPU 來壓 dirty rate（`MIGRATE_AUTO_CONVERGE`，§8.3），對延遲敏感的工作負載在遷移期間會有感。若不能接受，設為 `false` 並倚賴 `allowWorkloadDisruption` 的暫停機制。

```bash
# 若為 False，message 會直接對應 §8.7 的九項之一
```

## §12 待驗證清單

### [RT] 必須在你的叢集執行

1. virt-launcher 內實際的 QEMU／libvirt 版本（§1.3）
2. node kernel 版本（影響 §2.4 的 tun 行為）
3. `cpumanager=true` 的 node 數量與空閒獨佔 CPU（§6.2）
4. hugepages allocatable（§6.5）
5. host CPU model node labels 的同質性（§8.6）
6. 套用後的 `LiveMigratable` condition（§10）

### [EXP] 需要實測，本文不給數字

| 實驗 | 對照組 | 量測方式 |
|---|---|---|
| E-1 masquerade vs bridge 的延遲差 | 兩支除 binding 外完全相同的 VM | guest 內 ping／`netperf TCP_RR`，取 p50/p99/p99.9 |
| E-2 multiqueue on/off | 同上，只切 `networkInterfaceMultiqueue` | 多條並行 flow 的吞吐 + 單 flow 延遲（預期單 flow 無改善） |
| E-3 `dedicatedCpuPlacement` + `isolateEmulatorThread` 的抖動改善 | Tier A vs Tier B | 延遲 p99.9 與 max，host 上並跑吵鄰居負載 |
| E-4 hugepages 的邊際效益 | Tier B 開/關 hugepages | 同 E-3 |
| E-5 遷移期間的延遲與停機 | Tier B + MigrationPolicy | 遷移全程持續 ping，量中斷長度；同時抓 `virt-launcher` log 的 `ExpectedDowntime` |
| E-6 `allowAutoConverge` 的節流代價 | MigrationPolicy 開/關 | 遷移期間 guest 內的延遲劣化幅度 |
| E-7 §2.2 的推論驗證 | `allowEmulation` 叢集 + multiqueue | 確認 domain 是否真的啟動失敗（驗證 **[INF]** 是否成立） |

**[EXP]** 建議把 E-1～E-4 當成一組正交實驗（每次只切一個變因），先跑 E-1（預期效益最大）再決定是否值得付 Tier B 的維運成本。
